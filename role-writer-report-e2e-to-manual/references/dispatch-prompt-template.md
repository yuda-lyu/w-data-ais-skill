# 派工提示骨架與驗收表

主代理把「一個流程的手冊內容」派給子代理時，提示須自足（子代理看不到本技能與對話），下列各段缺一不可。以 `<…>` 為佔位，派工時全部代入絕對路徑與實際值。

## 1. 提示骨架

```
你是報告撰寫者。任務：為「<系統名>之使用者操作手冊」撰寫<瀏覽|編輯>類 E2E-<起>～E2E-<迄> 共 N 個案例之手冊內容（圖名與圖文敘述），<建立新的|寫入既有>內容檔。全程用繁體中文。

## 專案與檔案（皆為絕對路徑，不要 cd）
- 專案根：<絕對路徑>
- spec（真理源）：<絕對路徑>（先整篇讀完，含「畫面元素對照」與「已知落差」）
- 標準圖：<絕對路徑>/<流程前綴>-<圖鍵>.png（<寬×高> 截圖，每張恰有一個紅框）
- 你要修改的唯一檔案：<content 檔絕對路徑>（<已有 E2E-001 範例，不得改動，在其後依序追加|格式完全比照同夾既有之 <另一流程>.mjs，先讀它當範例>）
- 產製程式（先讀懂驗證邏輯，不要改）：<共用模組與薄殼路徑>
- 內容檔格式：每案例 `{ figs: { 1: '圖名', ... }, text: '敘述', skipImgs: ['圖鍵'] }`；figs 之序號 k 對應 spec 該案例「視覺」段所列圖鍵之順序（略過 skipImgs 者後重新從 1 編號）；text 以 `{fig:k}` 引用第 k 張圖。

## 工作流程（每個案例都要走完）
1. 讀 spec 該案例之 title / description / flow（含操作、驗證之語意與視覺段、備註）。
2. 以 Read 工具逐張開啟該案例所有標準圖並仔細看（絕不憑檔名或 spec 想像畫面）：紅框框住什麼、畫面上實際出現之彈窗標題、按鈕文字、提示訊息、標籤文字。以 Glob 確認每張圖檔存在；spec 列有但檔案不存在者（已知：<圖鍵清單或「無」>）放入 skipImgs，文中改以文字說明該步結果。
3. 撰寫 figs 與 text。
4. 全部寫完後執行 `node "<genMd 絕對路徑>"` 驗證（檢查每張圖有圖名、末字為「圖」、無英數符號、每張圖恰被引用、無多餘引用、全冊不重名），必須無錯誤結束；提示「尚未撰寫之案例」只含 <另一流程前綴> 者屬正常。不要執行 g.mjs / genFigs.mjs / genDocx.mjs。

## 圖名規則（figs）
- 純中文、8～14 字、末字必為「圖」；不含底線、半形括號、{}、|、英文（固有名詞例外但盡量避免）；不得夾帶案例編號或序號。
- 點擊前之圖以「點選○○圖」命名（○○＝按鈕或項目名），點擊後之圖以結果命名。
- 同案例內、全冊皆不得重複；同一動作多節出現時加語意前置語（另存前／刪除前／確認刪除○○）。

## 敘述規則（text）
- 基於 spec 之 description 改寫為操作手冊口吻，依操作順序逐步敘述，每一步接「，如{fig:k}所示」（置該子句末），每張圖恰引用一次且依 k 順序；結尾可補一句適用情境或注意事項。一段為原則，過長可用 \n\n 分兩段。
- 確定語氣、使用者視角。畫面元素名稱照畫面實際文字逐字（含半形括號、底線、「[測試]」前綴）：選單項目、資料夾、清單列、欄位、標籤、彈窗標題、選單內項目用「」；可點之按鈕與圖示鈕用【】。
- 承接式前置以使用者語言重述（如「開啟「○○」之抽屜並展開進階功能選單後」）；不得寫「承 E2E-001」「見 2.1 節」「詳如前」。
- 全形標點，英文詞組內部半形；數字與英文兩側空格沿用 spec description 之寫法。
- 禁用：<專案禁詞清單全文：破折號、箭頭、段中粗體、括號過長、段首連接詞、測試用語（本案例／測試／e2e／標準圖／紅框／spec／seed）、file:line、元件名、程式名、簡稱、以及裁決表所列詞>。
- 隨種子資料變動之數字（筆數）不寫；結構性數量可寫。測試輸入值含測試字樣者改中性描述。
- 彈窗標題、按鈕文字、提示訊息照圖與 spec 逐字引用，置於「」內。
- 系統名一律全稱。<編輯類：於各案例首句提一次「具編輯權限之使用者」。>
- 敘述內容必須與該張圖實際畫面相符；spec 與圖不符時以圖為準並在回報中列出。

## 守則
- 暫存檔一律放 <專案根>/tmp/；不得修改內容檔以外之任何檔案；不得刪除或重產任何標準圖。
- 用 Read/Edit/Write/Glob/Grep 工具處理檔案，不用 cat/heredoc/sed。

## 回報（最後訊息）
1. 已撰寫案例清單與各案例圖數。
2. skipImgs 清單。
3. spec 與圖不符或畫面有疑義之處（附圖鍵）。
4. genMd 驗證輸出之最後三行。
```

## 2. 派工前主代理必做

- 已用同一版式產出一節樣板並經使用者確認；共用模組與內容檔範例（第一案例）已存在，子代理有可抄之實例。
- 已把 spec 中會進表格之 title／description 過一遍 lint 風險（佔位、箭頭、禁詞、括號過長），先改 spec。
- 標準圖夾與 spec 圖鍵已比對一致；pending 之圖鍵已知並寫進提示。
- 模型：內容撰寫需逐張讀圖與判斷，派 Opus；純機械（抄薄殼、改 config）派 Sonnet。

## 3. 收回驗收表（逐冊）

| 項目 | 判準 |
|---|---|
| 回報四項齊全 | 案例與圖數合計＝spec 可用圖數；skipImgs 只含已知 pending；末三行為 genMd 零錯 |
| 逐案例審稿 | 語氣、「」【】標記、承接前置、無測試用語與禁詞、無種子數字、無「不受影響」類未驗證斷言、無無依據收尾句 |
| 抽圖核對 | 每冊至少抽開 10% 之圖（含每類：點擊前、結果、彈窗、訊息），敘述與畫面相符 |
| 不符清單裁定 | 每條開圖確認後三選一：改 spec（同步測試檔）／退回 e2e 重產／照圖寫；裁定寫入 L3 或已知落差 |
| 產製 | 主代理統一跑 genFigs → genMd → genDocx → lint；docx 以實體檔驗證 |
| 中斷處置 | 子代理 429／529 中斷：檢查內容檔語法與已寫案例，剩餘由主代理逐張看圖接手 |
