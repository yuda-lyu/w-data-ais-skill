# 完整範例：一份短報告從 Step 0 走到 Step 8

這是一個真實案例（2026-08-30），用來示範每一步的產物長什麼樣。被驗證的「報告」是為技能 `dispatch-codex` 新寫的一節說明文字，內容描述 Codex CLI 在 Windows 上的沙箱前置設定。引用的檔案都在 `node_modules/w-dispatch-ai/`（1.0.19），行號以該版本為準。

## 任務

使用者原話（兩句）：

1. 「我剛更新 w-dispatch-ai 請確認」
2. 「請針對技能 dispatch-codex 去調整，因 windows 沙箱得要先設定好才能讓調用 codex cli 內 ai 具備讀寫之類的權限，請務必要添加至技能說明，否則一直不能用又不知道問題原因」

## Step 0：讀懂任務，選層，寫計畫

需求條目（逐句取自原話）：

- R01 確認 w-dispatch-ai 已更新到新版，且技能與新版契約一致。
- R02 在 dispatch-codex 技能說明中加入 Windows 沙箱前置設定，讓執行者知道「不能讀寫」的原因與解法。

類別判斷：R02 說的不是「加一句話」，而是「Windows 上 Codex 無法讀寫」這整個故障類別——原因、判別方式、正解、替代方案、失敗時的症狀，都屬於要交的範圍。

報告類型：描述程式／系統行為 → 依決策表做 L0a、L1、L2、L3；L4、L5 不適用（單次交付、無領域專家）。

`./tmp/validate-plan.md`：

```
類型：描述程式／系統行為
做：L0a 實體存在、L1 主張溯源、L2 實跑（有 ls、codex --version 可跑）、L3 反向覆蓋
不做：L4（無外部專家，使用者本人即審核者）、L5（單次交付）
```
