# 跨流程共用文件（設計要點與取捨）之章節、裁決紀錄與登記

多份流程 spec 共通之規則不各自重抄，集中於一份共用文件；檔名在同組織各專案固定一致（慣例為 `spec/設計要點與取捨.md`，不自創「共用約定」「共用規則」等別名），讓專案間可用同一路徑互相引用。各流程 spec 與本檔衝突時，以流程 spec 明文為準並於該處說明理由（視為刻意之個別偏離）。

## 1. 內容兩類，同一檔

### 1.1 跨流程設計決策（ADR 段落）

`ADR-NNN`：Status／Context／Decision／Consequences／Affected。修改時新增新條並把舊條標 Superseded，不刪舊條。業主裁定之產品行為（如「入口參數須照畫面權限限制」）修復後即以 ADR 登錄。

### 1.2 各流程 spec 共通之約定（章節建議）

| 章 | 內容 |
|---|---|
| 文件範圍與命名 | 流程文件之命名規則；瀏覽／編輯分檔；flow 代號登記表（系統 → 選單顯示文字（無主選單入口者明標）→ 流程前綴 → spec 檔 → 標準圖夾） |
| 語系 | 有 i18n 者各語系一輪；單一語系載明省略 |
| 標準圖之命名與存放 | `<流程前綴>-E2E-NNN-<序>-<kebab>.png`；每步兩張；一圖一框；框實際內容；訊息圖之截法；暫時狀態圖「產製照產、比對略過」之政策 |
| 資料庫重置 | 快照來源、重置粒度（每案例／每檔）、具名資料之複驗狀態表 |
| 副作用與清理對照 | 見 case-format.md §6（含後端於既定資料夾以外寫出之檔案） |
| 軟刪除與硬刪除 | 語意定義與各流程之適用 |
| 共用元件與重複覆蓋之避免 | 共用元件之驗證歸屬（在哪個流程驗一次，其他流程只驗可開啟）；**同型元件之操作序列登記**（如「展開清單 → 點選項」四張），姊妹流程與姊妹系統對齊 |
| 截圖穩定性之共通處置 | 固定時鐘、動態內容之覆蓋策略、畫布類系統之比對策略、首頁即時數值區之集中覆蓋；**測試環境呈現**清單（會出現在標準圖但正式環境沒有之現象） |
| 訊息文字之取用方式 | 訊息一律取自定義處原文並附位置；短暫訊息之時機寫實測值 |
| spec 之事實來源 | 只認現行程式碼（含共用元件庫與上游套件之原始碼）、產物與實機；舊文件與舊草稿不作依據 |
| **權限模型與測試帳號矩陣** | 權限軸盤點表（permission-and-accounts.md §1～§2）、帳號矩陣（§3）、缺口清單（待增設之組合）、各軸之判定位置 |
| **資料主從** | 多系統共享資料之主從表（permission-and-accounts.md §6）、同步方式與週期、次系統可否編修 |
| 入口與版面之共通事實 | 主選單於基準視窗之可視範圍、需捲動之項目、內部捲動容器之系統 |
| **裁決紀錄** | §2 之格式；設計事實與已修復者不在此列（已修復者改以 ADR 登錄） |
| 上游套件事項之歸屬 | 各流程〈已知落差〉中歸屬上游套件或共用元件庫者之彙整：套件名、條目、轉交方式（建議檔／issue）、狀態（已轉交／已收回／已修復於版本）；建議檔或 issue 收回後條目仍留此表 |
| description 撰寫風格 | 引用 case-format.md §2 之定位、寫成什麼、不得出現、六問、驗收 |
| 證據目錄 | 探測 log 與佐證之固定目錄（慣例 `spec/evidence/`）、命名（帶輪次或日期、不覆蓋） |
| 變更紀錄 | 日期＋輪次＋摘要（哪些流程、改了什麼、為何） |

## 2. 裁決紀錄（每條一列；被責備「這之前說過」即代表本表漏登或漏查）

| 日期 | 原問題（一句） | 裁定（逐字或摘要） | 適用範圍 | 對 spec 之效果 |
|---|---|---|---|---|
| YYYY-MM-DD | 紅框畫在同色按鈕上不易辨識 | 暫不處理，待業主審查後再議 | 全部流程 | 不再列入回報 |
| YYYY-MM-DD | 非管理者可進入受限之後台版面 | 刻意設計，支援未來功能 | 該子系統 | 設計事實；不列擴充建議 |
| YYYY-MM-DD | 隱藏欄位再顯示置於最右 | 表格元件為拖曳換序之刻意設計 | 全部使用該元件之頁面 | 設計事實；不建議元件調整 |
| YYYY-MM-DD | 某頁用原生下拉 | 元件選型由套件決定；改元件時 e2e 跟著改 | 全部 | 不列缺陷 |

規則：

- 口頭裁示當日登記，不等下一輪；跨專案通用之裁示（元件層、安全設計）另寫入代理記憶，供他專案沿用。
- 每次要寫「待裁示」「建議」之前，先查本表；已有者引用列號，不重提。
- 業主逐字裁定之句子登記為定稿句；改動須明示。

## 3. 與專案設定檔之同步

- 專案之 e2e 映射表（各流程之測試檔、標準圖夾、案例數、偏離紀錄）與本檔之 flow 代號表須一致；新增系統時兩處同步。
- 手冊 lint 之禁詞裁決表、放行詞（畫面上之資料項名稱）與本檔之 description 風格章節三處一致；使用者裁定新規則時同時登記。
- 帳號矩陣與登入系統／權限系統之種子同步；種子改版即重驗矩陣。
- 上游套件版本與其畫面影響之紀錄與專案之處理要點同步（升版後三件事，lifecycle §4）。

## 4. 變更紀錄之寫法

每輪改寫記一段：日期、對象（哪些 spec、幾條案例）、改了什麼（如「description 全面改寫為手冊敘述」「視覺段改為逐張列圖鍵並括號寫框住元素」「原載遮罩不成立已改」「E2E-00X 因產品修復同號改寫」「E2E-00Y 因元件改為自製而拆為兩步四張」）、依據（實測 log、審圖退件、使用者裁定、產圖後對帳、套件版本）。讓後來者能判斷某句是哪一輪、為何而改。
