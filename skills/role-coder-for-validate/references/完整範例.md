# 完整範例：一個小任務從 Step 0 走到 Step 9

這是一個**示意任務**（不是任何專案的實際改動），用來示範每一步的產物長什麼樣。任務所引用的既有程式是實際安裝的 `w-dispatch-ai` 1.0.19（`node_modules/w-dispatch-ai/src/dispatchCodex.mjs`）與 `wsemi` 1.8.80，行號 2026-08-30 核對；新增的函式、測試名、輸出數字都是示意。

## 任務（示意）

使用者原話：「dispatchCodex 在 Windows 上，如果 Codex 的沙箱還沒設定好，就不要派工，直接回錯誤結果，不然它會靜默失敗。」

## Step 0：需求述語化

需求條目與述語：

| 需求 | 述語 |
|---|---|
| R01 Windows 上沙箱未設定時不派工 | P1：在 `process.platform === 'win32'` 且 `~/.codex/.sandbox/setup_marker.json` 不存在時，回傳 `{ ok: false, error: <含 'sandbox' 字樣> }`，且不呼叫 `execCli` |
| R01 | P2：marker 存在時，行為與改動前完全相同（args、stdin、timeout 都不變） |
| R01（隱含） | P3：非 Windows 平台不做這個檢查 |
| R01（隱含） | P4：呼叫端可以關掉這個檢查（向後相容；既有呼叫端可能刻意用 `windows.sandbox="unelevated"` 繞道） |

歧義：P4 是我的推斷，不是使用者原話——寫進 plan 標為假設，並在回報中問使用者一個具體問題：「要不要提供 `skipSandboxCheck` 選項讓走 unelevated 繞道的呼叫端關掉檢查？」

類別判斷：使用者說的是「靜默失敗」這一類。本次只做「未設定就不派工」；「被擋時回覆合法字串通過 nonempty」屬同類但另一個點，寫進 plan 的「已知未做」，回報時提出。

## Step 1：約束、對標、輸入空間表、選層

約束：不改 `execCli` 的呼叫方式；不改既有預設值（`DEFAULT_SANDBOX`，`dispatchCodex.mjs:37`）；不把 unelevated 設為預設（套件 README.md:246 明文刻意不設）；函式不 reject，一律回結果物件（`dispatchCodex.mjs` JSDoc 明文）。

對標：Playwright 與 Puppeteer 在瀏覽器執行檔不存在時，都是在 launch 前就丟出含路徑與安裝指引的錯誤，不會等到 spawn 失敗才靜默；本系統差異是「spawn 成功但命令全被擋」，錯誤發生在更後面，所以前置檢查有必要——標為「缺陷（本次修）」。

輸入空間表（軸：平台 × marker 狀態 × 關閉檢查選項）：

| 平台 | marker | 關閉檢查 | 現況 | 應然 | 處置 |
|---|---|---|---|---|---|
| win32 | 不存在 | 否 | 派工後靜默失敗 | 回 `ok=false`，不 spawn | 本次修（P1） |
| win32 | 不存在 | 是 | 派工 | 派工（呼叫端自負） | 本次做（P4，待使用者確認） |
| win32 | 存在 | 否／是 | 派工 | 派工，行為不變 | 回歸（P2） |
| 非 win32 | 任意 | 任意 | 派工 | 派工，不檢查 | 本次做（P3） |

選層：純函式改動，涉及檔案系統（讀 marker）與外部 CLI → L0a–L0d、L1、L2（真的 spawn 一次確認 marker 存在時行為不變）、使用者視角以真指令跑一次；L3、L4、L5 e2e、L6 不適用。
