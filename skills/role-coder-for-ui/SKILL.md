# 前端 UI 實作規範

**觸發條件**:凡涉及前端畫面/元件/互動之改動,本篇整篇入 context 逐項比對後才動工——即使任務被框成[功能搬移/重構/修 bug]而非[設計].觸發一律以對象(畫面,元件,排版,展示欄位,互動指示符號)解讀,不以任務類型窄讀.

**與其他技能之分工**(命中者一併調用,本技能各條仍適用):

- 「重新設計」「重做」「redesign」「要有設計過 / 設計感」,或對美感 / 版面 / 比例 / 對齊 / 留白 / 風格表達不滿 → skill[role-design-web-for-redesign].
- Vue 非同步提交流程,template `@event` handler,`promiseUnlock` 按鈕,單例對話框 → skill[role-coder-for-vue-ui].
- e2e 測試與標準圖 → skill[role-coder-for-test-e2e].

## 0. 依任務找章節

| 任務 | 必看 |
|---|---|
| 任何 UI 改動 | §1,§2,§5 |
| 建置或修改展示項目資料之頁面/彈窗(read-only viewer 類) | §3 |
| 搬移/分拆/接排既有元件,調整定位,新增下拉/輸入框/chip/badge/膠囊 | §4 全部 |
| 讀到或改到任何既有互動指示符號(箭頭/chevron/把手/開關/hover 放大/cursor) | §4 第 4 條 |
| 要在畫面上用原生 `<select>` | §4 第 3 條 |

## 1. 基本原則

- 新增功能時絕不修改既有 UI,版面,陰影,視覺效果.
- 視覺效果(過場,陰影,hover)在相關元素類型間須一致,主動驗證不等使用者指出.
- 非使用者同意不可修改既有範例的拼寫.

## 2. 禁用瀏覽器內建 `alert()` / `confirm()` / `prompt()`

production code 一律改用專案既有 DOM 模態元件(grep `WAlert` / `CheckYes` / [System message]用法沿用);僅臨時 debug 可短暫用,不得留進 commit.why:原生 dialog 是 OS 層視窗不在 DOM——Playwright 截不到圖,要掛 `page.on('dialog')`,block JS 執行緒,UX 不一致不可樣式化;DOM 模態則 locator + 文字斷言 + pixel baseline 全可測.看到既有 `alert()` 應提報並經同意後改 DOM 模態.

## 3. 展示形式須匹配欄位型別/語義,交付前逐欄自掃,不等使用者抓

**觸發**:建置或修改任何[展示項目資料]頁面/彈窗(read-only viewer 類).

**問題根源(LLM 天性)**:建 viewer 時傾向把所有欄位機械複用同一種[label+文本框]組件,純數值(如座標 200)孤懸於全寬多行框內,一看就是未經設計.此類錯配使用者一眼可見,LLM 卻不會自覺——因為[每欄都套同組件]在程式上是最省事路徑.

**強制流程**:

1. **動工前先讀 schema 按型別分流**:專案 schema 通常帶有欄位型別與單位資訊(欄位名各專案不同,先在該專案的 schema 找出[型別]那一欄),展示形式依型別選擇:
   - 純數值 → 緊湊統計格(label 小字+等寬大號數值+單位小字,一組相關數值並排)或單行呈現,**絕不用全寬多行文本框**
   - 百分比/進度語義 → 進度條
   - 枚舉/分類/關鍵字 → chip/badge
   - 多行長文本 → 文本區塊(這是文本框唯一正當場景)
   - URL → 可點連結;日期 → 格式化短文本
2. **檢核反射**:寫每個展示欄位時自問[這欄的值平均多長,什麼型別?]——值短(數字/代碼/枚舉)卻配全寬多行框＝錯配,當場改.
3. **交付前逐欄自掃一輪**:對整頁每個欄位跑一次檢核反射,並確認同型別欄位跨系統/跨頁面呈現一致(同專案已有 canonical 數值展示組件就沿用,沒有就建一個供全專案復用).
4. 此原則不限數值:任何[呈現形式與資料語義不匹配]皆屬同類問題(如布林用長文本框,顏色值用純文字不帶色塊預覽),一併自掃.

## 4. 觸碰既有排版或新增小元件:量數字+盤色票,工程任務也適用

**觸發**:凡動到既有元件之排列(搬移/分拆/接排按鈕群,調整定位)或新增任何小型 UI 元件(下拉/輸入框/chip/badge/膠囊)——**即使任務被框成「功能搬移/重構」而非「設計」**;第 4 條另於**讀到或改到任何既有互動指示符號/affordance 時**觸發(不限新增).
**背景(LLM 天性)**:把重新設計(skill[role-design-web-for-redesign])之量測義務窄化成只有[重新設計]觸發詞才啟動(觸發一律以對象解讀,不以任務類型窄讀);順手改排版/新增小元件被歸成工程任務→整套[讀API→量數字→盤設計語言]被跳過;配色走[隨手給個看似合理的色]之最省事路徑.
**典型錯誤形狀**:按鈕群拆搬後接排間隙量到 17px、原生只有 5px,未量測即交付;新下拉未盤點父層深色玻璃色票就隨手配色.

1. **排版數字前後對照**:動工前量原始排版數字(間距/對齊/尺寸,`getBoundingClientRect` 取真值),改後複量同組數字,一致才可宣告完成.只驗[功能會動][有排上去]＝未完成.
2. **配色先盤點後沿用**:動工前盤點[所在組件+鄰近組件]之色票並明文列出——主題(焦點/選中)色,hover 色,底色層次,文字階層,邊線色;新元件一律沿用,禁止憑空配色(隨手挑深色/淡色也算憑空).無可參考時才允許新色且須先報備.
3. **原生 `<select>` 禁入自訂主題區**:其彈出清單之選中/highlight 色由 OS/瀏覽器決定(如 Chromium 淡藍),CSS 不可控;頁面有自訂主題(深色玻璃等)一律改用專案自製 popup 選單(如 WPopup)重現主題,原生 select 僅限無主題要求之內部頁.此為 §2 禁用原生 dialog 之同族規則.
4. **互動指示符號是行為承諾,兌現不了就移除(新增與既有皆適用)**:箭頭/chevron/把手/開關/hover 放大/cursor 等符號暗示[可互動+有狀態];放了就必須完整兌現;**讀到既有碼有承諾無行為者,一律列為缺陷(有承諾無行為＝半吊子,發現即修或移除),不得抄成[設計如此]之註解**.兌現的標準——尺寸可辨識,且狀態聯動(如下拉開啟時箭頭旋轉或高亮).狀態接不出來或不打算接時一律不放,由容器自身之 hover 回饋指示可點即可;半吊子指示比沒有更糟——靜止不動的▾會被使用者當成壞掉/功能瑕疵.**典型錯誤形狀**:下拉配一個 0.6rem、永遠朝下、不隨開闔變化的 ▾.
5. **固定尺寸給值須計算,不可拍腦袋**:給固定 width/height 前,先量內容最長項實寬(隱藏span量測或 getBoundingClientRect)+組件內部結構(padding/邊框/icon/間隙)逐項加總,再留小而對稱之呼吸空間(數px級);猜一個[看起來夠]的值→過寬右側大片留白,過窄截字,皆為未經設計.**典型錯誤形狀**:最長內容(如 `'2:2'`)實寬僅 16px、結構加總自然寬約 50px,卻拍腦袋給 74px → 右側留白突兀.
6. **下拉/選單之高亮不可破壞文字對齊參考線**:選項文字左緣須與 trigger 內文字左緣貼齊(padding 對齊,量測驗證);選中高亮用[不佔位.不干擾對齊]的方式(整列填色/文字變色),左緣bar.前置icon.縮排等會在文字左側添加視覺元素之高亮,於窄選單會讓文字看起來右偏.對齊參考線變亂,禁止照搬自寬列表之高亮語言.**典型錯誤形狀**:54px 的窄選單照搬寬列表的左緣 bar 高亮,選項 padding(13px)又與 trigger(9px)不一致,雙重破壞對齊.

## 5. 交付前勾選清單

逐項打勾才可宣告完成;不適用者寫明[不適用]與理由,不可留空.

- [ ] 沒有動到需求以外的既有 UI,版面,陰影,視覺效果(§1)
- [ ] 相關元素類型間之過場,陰影,hover 一致,已實際操作確認(§1)
- [ ] 沒有改動既有範例的拼寫;要改者已取得使用者同意(§1)
- [ ] 沒有新增 `alert()` / `confirm()` / `prompt()`;讀到既有者已提報(§2)
- [ ] 展示欄位已逐欄自掃:展示形式對應型別,短值沒有配全寬多行框,同型別跨頁一致(§3)
- [ ] 動到排版者:改前改後各量一次同組數字,兩次一致(§4 第 1 條)
- [ ] 新元件配色取自已盤點並列出之色票,沒有憑空配色(§4 第 2 條)
- [ ] 自訂主題區沒有原生 `<select>`(§4 第 3 條)
- [ ] 每個互動指示符號都有對應行為且狀態聯動,兌現不了的已移除(§4 第 4 條)
- [ ] 每個固定尺寸都有量測與逐項加總之依據(§4 第 5 條)
- [ ] 下拉選項文字左緣與 trigger 貼齊,選中高亮不佔位(§4 第 6 條)
