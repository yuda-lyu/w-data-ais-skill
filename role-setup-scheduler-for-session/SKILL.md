# role-setup-scheduler-for-session — Session 內定時巡檢設定要點

## 概述

把「定時檢查某個排程管線是否正常，異常就診斷並修復」交給 Claude session 自身的排程執行。核心來自 `c:/tai-news` **實際運作 20+ 次巡檢任務後歸納**的做法。

**與作業系統排程的分工**：作業系統排程（見 `role-setup-scheduler-for-windows`）只能依預寫規則告警；session 排程的獨特價值是**能查證、判讀、改碼、驗證**——即「為什麼怪怪的」而非只是「有沒有掛」。

- **適用**：管線改動頻繁、需要判斷力的巡檢期間
- **不適用**：長期無人值守的存活告警（見 §7）

## 何時使用此 Skill

- 要讓 Claude 每隔一段時間自動檢查某條管線是否正常
- 巡檢發現異常時要能自主診斷並修復
- 要撰寫巡檢用的自足 prompt
- 要規劃巡檢紀錄的格式與內容

---

## 1. 機制的硬限制

`CronCreate` 建立的是**對話內排程**，不是作業系統排程。以下決定成敗：

| 限制 | 影響 | 對策 |
|---|---|---|
| **Session-only**，不寫入磁碟 | session 結束即消失 | 結果必須落檔（§5）；重開 session 要重建 |
| **僅於 REPL 閒置時觸發** | 正在跑長任務時會被順延 | 選時間點時錯開管線自身的忙碌區間（§3） |
| **7 天後自動到期** | 跑最後一次後刪除 | 屆期前需重新建立 |

> ⚠ **`durable` 參數沒有作用**——工具定義明載「durable persistence is not available，All jobs are session-only」。**不要以為設了它就能持久化。**

### 觸發時間會比設定值晚：兩個疊加成因

**成因一：系統性 jitter（工具內建）**

排程器會在你指定的時間上**加一段確定性抖動**：

- **recurring 任務：最多延後該週期的 10%，上限 15 分鐘**（例：每小時任務 → 最多晚 6 分鐘；每日任務 → 最多晚 15 分鐘）
- one-shot 任務若落在 `:00` 或 `:30`：最多**提早 90 秒**

**成因二：REPL 忙碌順延**

任務只在對話閒置時才會觸發，正在跑長任務就得排隊。

> **實測佐證（tai-news）**：排程設每時 `:10`，連續八次實際抵達都是 `:26`——延遲約 16 分鐘。
> 以每小時任務的 jitter 上限 6 分鐘計，**其餘約 10 分鐘來自對話忙碌**（當時在跑端到端驗證）。
> 此為機制正常行為，非任務失效；使用者若在 `:23` 問「為何沒回報」，答案通常是「還沒到」。

**實務意義**：巡檢的時間精度只到「約莫那個時段」，**不要據此設計需要精準對時的流程**。

## 2. 先確認該用哪個工具

| 需求 | 該用 | 理由 |
|---|---|---|
| 每隔 N 分鐘／小時**主動巡檢**一次 | **`CronCreate`** | 固定牆鐘週期重跑 prompt |
| 要在檔案／行程／指令輸出**一有變化就立刻知道** | **`Monitor`** | 串流事件、即時觸發；cron 是輪詢 |
| 長期無人值守的存活告警 | **作業系統排程** | session 不會一直開著（見 §7） |
| 「N 分鐘後提醒我一次」 | `CronCreate` + `recurring: false` | 觸發一次後自動刪除 |

> 工具定義明確指出：**要即時盯 log 或行程變化請用 `Monitor`，不要用 cron 輪詢**。

## 3. 建立

```
CronCreate({
  cron: '10 * * * *',      // 每小時 :10
  recurring: true,         // 預設 true；一次性提醒用 false
  prompt: '（完整巡檢指令，見 §4）',
})
```

**選時間點的兩個原則**：

1. **錯開被巡檢管線的執行區間**——管線整點啟動、實測 1~5 分鐘內結束，故巡檢設 `:10`。若管線最壞要跑 14 分鐘，就設 `:15` 以後。
2. **避開 `:00` 與 `:30`**——這兩點是所有人的預設值，全球請求會同時打到 API。工具定義也明確建議挑非整點分鐘（如 `7 * * * *` 而非 `0 * * * *`）。

### 一次性任務（`recurring: false`）

用於「某時做一件事」而非週期巡檢。須把分／時／日／月都釘死：

```
CronCreate({
  cron: '30 14 <日> <月> *',
  recurring: false,
  prompt: '檢查今日部署是否完成',
})
```

## 4. prompt 的撰寫要點

排程觸發時是**獨立的一輪對話**，讀不到「前面說過的內容」。prompt 必須自足，且包含下列六項：

### 4.1 檢查對象的絕對路徑與識別名

日誌目錄、排程任務名稱都要寫死絕對值：

- 日誌：`c:/tai-news/log/{今日}/{YYYYMMDDHHmmss}.log`
- 排程：`Get-ScheduledTask -TaskName 'trigger-news-ai' | Get-ScheduledTaskInfo`

### 4.2 明確的正常／異常判準（必須可機械判定）

不能寫「看起來正常」。tai-news 用的是：

> **正常** ＝ 日誌末行有「任務完成」，**且**出現「已發送 Telegram」或「已通知」，**且** `LastTaskResult=0`
> **異常** ＝ 上述任一不成立、日誌中有 ERROR、或**該跑的時段完全沒有產生日誌檔**

**最後一條最容易漏掉，卻最重要**：沒有日誌檔代表程式在「建立日誌之前」就崩潰了（相依套件缺失、語法錯誤），此時什麼線索都不會留下。判準要一併寫明處置方式：**手動執行一次以取得真實錯誤訊息**。

> **實測價值**：tai-news 曾因全域相依被清除而在 import 階段崩潰，連失敗通知都發不出，**靜默壞了 6 天**才被發現——正是這條判準要抓的情形。

### 4.3 關鍵陷阱：`LastTaskResult=0` 不等於成功

管線若**自行捕捉錯誤並優雅結束**，作業系統看到的仍是「正常退出」。tai-news 就發生過：整批新聞遺失、只發出「選文失敗」通知，但 `LastTaskResult` 仍為 0。

**故不可只看排程狀態，必須讀日誌確認有成功標記。**

### 4.4 異常時的處置授權與界線

要給修復權限，否則巡檢只能告警而失去價值。但必須寫明界線：

```
- 先查證再動手，不要憑猜測改動；技術細節不確定時實測或查證。
- 只做最小必要修改，不重構。
- 【絕不可改】列出會造成不可逆損害的項目。
  例：不改去重鍵 sha1(url.trim())（會使 52k+ 筆舊資料全部重推）、
      不改資料庫 db／cl 名稱（會指向空集合）。
- 修完後實際執行一次驗證。
- 暫存檔一律放 ./tmp/，用完清掉。
```

> **「絕不可改」清單是最重要的部分**——它把「AI 自主修復」的爆炸半徑限制在可接受範圍內。

### 4.5 結果寫入檔案

見 §5。

### 4.6 回報格式

正常時只回一行，避免每小時洗版；異常時才展開。prompt 內直接指定格式：

```
## YYYY-MM-DD HH:mm — 正常（{耗時}s，{N}/{M} 篇有摘要）
```

並要求**用實際絕對時間，不要用「今天／剛才」等相對詞**——巡檢紀錄會被日後回讀，相對時間屆時無法解讀。

## 5. 結果必須落檔

**理由**：session 隨時可能結束，屆時對話內的所有巡檢結論一併消失。落檔後即使排程失效、session 重開，歷史與待觀察事項仍在，新 session 可直接接續。

tai-news 寫入 `./監控運維紀錄.md`，以**追加**方式（明確要求「用 Edit 追加，不要覆寫整份檔案」）。

### 檔案該記什麼

| 情況 | 記法 |
|---|---|
| 正常 | 一行：時間、耗時、產出量 |
| 正常但有值得留意的現象 | 一行 ＋ 簡短註記（例：某供應商耗時逼近上限） |
| 異常 | 一節：**現象 → 根因（附證據）→ 處置 → 驗證結果** |
| 做了改動 | 變更表（哪個檔、改什麼、為什麼），含**實測數據** |

**根因務必附證據**：`file:line`、實際錯誤訊息、或實測數列。只寫「疑似服務不穩」對日後毫無幫助。

### 也要記「決定不處理」及其理由

這點與記錄問題同等重要。例：

> deepseek 回應時間波動（12~139s），但全部遠低於 300s 逾時上限、摘要每次皆完整產出。
> 維持觀察不處置——真正需處置的判準是「出現逾時或連續驗證失敗」，單純變慢不構成損失。

否則下一輪巡檢（或另一個 session）會重新糾結同一件事，甚至為了消除假想風險而引入真實退化。

## 6. 巡檢時的實務要點

以下是實際跑了 20+ 次後才浮現的問題：

### 6.1 檢查前先確認該時段是否已被檢查過

排程延遲會導致「使用者已提前手動問過、隨後排程才觸發」。tai-news 發生過：21:23 使用者提問時已檢查完 21:00，21:26 排程才到——此時應**確認紀錄檔中該時段是否已存在**，若已存在就不要重複追加，避免污染紀錄。

### 6.2 觀察事項要有明確的升降級判準

不要讓「待觀察」無限累積：

- **升級**：出現具體後果或逼近門檻時（例：耗時達逾時上限的 80%）
- **降級／結案**：連續 2~3 個時段回到正常區間即結案，並在紀錄中寫明「確認為單次波動，非趨勢」

### 6.3 處置門檻要事先想清楚

「服務變慢」與「服務不通」是不同性質：

> 單純變慢 → 不處置（遞補機制已涵蓋，管線仍成功送出）
> 出現逾時且**重複多個時段** → 停用該供應商（可逆的設定變更）

且處置要選**最小且可逆**的手段（加一行 `enable: false`），而非改動架構。

### 6.4 設「已知常態不回報」白名單

管線每輪必然出現的、已有機制兜底的警告，一律不展開說明，只在紀錄中帶一句「WARN 均為已知情形」。否則雜訊會淹沒真問題。

tai-news 的白名單：某 RSS 來源的上游 XML 格式錯誤、fetch-web 的逐層升級訊息。須展開的限於：**前所未見的錯誤字串**、管線未正常結束、有 ERROR。

---

## 7. 什麼時候不該用這個做法

Session 排程的本質是**對話內的提醒**，不是可靠的常駐監控。

| 面向 | Session 排程（`CronCreate`） | 作業系統排程 |
|---|---|---|
| 存活 | session 結束即消失 | 持續存在 |
| 到期 | 7 天 | 無 |
| 觸發精度 | 有 jitter ＋ 忙碌順延 | 準時 |
| 能否**診斷與修復** | ✅ 可（查證、判讀、改碼、驗證） | ❌ 只能依預寫規則告警 |
| 適用 | 改動期間盯穩定性 | 長期無人值守 |

**兩者互補**：長期用作業系統排程做「有沒有掛」的告警；改動頻繁的期間用 session 排程做「為什麼怪怪的」的深度巡檢。

若要長期化，把巡檢邏輯寫成獨立腳本（讀日誌 → 判定 → 異常時發通知），以作業系統排程執行（見 `role-setup-scheduler-for-windows`）——但要接受它只能告警、不能修復。

---

## 8. 維護

```
CronList()            // 確認任務仍在（只列得出本 session 的任務）
CronDelete({ id })    // 取消任務（id 由 CronCreate 回傳）
```

- **每次重開 session 都要重建**——目前無法規避（`durable` 無效）。
- 若長時間沒有巡檢回報，**第一件事是 `CronList`**，而不是去查被巡檢的管線。
- `CronList` **無法查證其他 session 的排程狀態**。
- 7 天到期前若仍需要，需重新建立。
