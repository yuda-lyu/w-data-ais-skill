# role-setup-scheduler-for-session — 讓 session 自己定時醒來做事

> 請照 §0 的五步順序執行，每一步都有明確的產物或判定；不要跳步，尤其不要跳過第一步（辨識環境）與第三步（驗證機制）。

## 0. 一分鐘看懂

**這個技能解決什麼**：讓正在對話中的 Claude session 在指定時間自己醒來，執行一段事先寫好的任務——最典型的是「每小時檢查某條管線有沒有正常跑，不正常就查證、判讀、修復、驗證」，也包括「N 分鐘後叫醒我做某事」「幾點以後才開始」「做完 A 等一段時間再做 B」。

**這個技能不解決什麼**：所有 session 內的機制都隨 session 消失（API 錯誤、連線中斷、IDE 重啟、視窗關閉即全滅）。需要「視窗關了也會準時啟動」的長期無人值守任務，要交給作業系統排程（見 `role-setup-scheduler-for-windows`）或 §6.4 的管線內建巡檢。

**五步流程**（後面各節依此順序）：

| 步 | 做什麼 | 產物／判定 |
|---|---|---|
| 1 | 辨識執行環境（§2） | 判定為「終端機 TUI」或「VS Code 外掛 headless」 |
| 2 | 依需求選機制（§3） | 選定 cron／背景計時器／Monitor／管線內建之一或組合 |
| 3 | 先驗證機制再依靠（§4） | `./tmp/sched_test/` 內有本環境的機制證據 |
| 4 | 撰寫自足任務書（§5） | 一份含六項必備的 prompt 或 md 檔 |
| 5 | 建立、執行、維護（§6–§9） | 排程在跑、紀錄檔持續更新 |

**三條鐵則**：

1. **先辨識環境再選工具**。VS Code 外掛內 `CronCreate` 與 `ScheduleWakeup` 建得成、列得出、但永遠不會響（§2）。在外掛內建 cron 然後等它，是本技能所有失敗案例的共同起點。
2. **任何推送機制上線前先驗證**。cron 送進來的 prompt 與人手貼的文字在對話中一模一樣，沒有來源標記；「一直沒動靜」與「正常但沒事發生」看起來也完全相同。沒有 §4 的證據就不能把它當監控依靠。
3. **喚醒後要做的事必須自足且落檔**。排程排的是一段 prompt（cron）或一次「叫醒」（計時器），不是任務本身；醒來時讀不到「前面說過的」，做完的結論也會隨 session 消失。

## 1. 名詞與執行模型

先把名詞定清楚，後面每個決策都依賴這一節。

| 名詞 | 定義 |
|---|---|
| **session 排程（cron）** | `CronCreate` 把一段 prompt 排入「本對話」的佇列；時間到，它以一則普通 user message 送進來，由主 agent 在自己的 context 內執行。不會另外 spawn agent，也沒有回報管道。工具契約原文：「Schedule a prompt to be **enqueued** at a future time」，`prompt` 參數為「The prompt to **enqueue** at each fire time」。 |
| **`ScheduleWakeup`** | `/loop` 動態模式用的喚醒工具，內部轉成一次性 cron，故與 cron 同命運。 |
| **背景計時器** | `Bash` 以 `run_in_background: true` 執行 `sleep N`；行程結束時 harness 送 `task-notification` 叫醒主 agent。**排的是「叫醒」，不是 prompt**——醒來要做什麼，必須寫在檔案裡。 |
| **`Monitor`** | 背景行程把 stdout 每一行變成通知推給主 agent；事件驅動，不需要任何 turn 來輪詢。 |
| **管線內建巡檢** | 被監控的管線在自己的收尾階段順手做機械檢查並寫紀錄檔；不依賴任何 session。 |
| **作業系統排程** | Windows 工作排程器等；持續存在、準時，但只能依預寫規則動作，不能判讀與修復。 |
| **自足任務書** | 醒來後要執行的完整指令（prompt 或 md 檔），不依賴對話脈絡即可照做。 |
| **巡檢紀錄檔** | 每次巡檢結論的落檔處；位置由使用者指定，未指定時放 `./tmp/<案名>/`（AI 暫存慣例）並於回報中告知，不得自行放進專案既有目錄（§5.1）。它同時是排程存活的證據。 |

### 1.1 cron 的三個推論

1. **prompt 必須自足**——它是新一輪對話的開場，讀不到先前脈絡（§5）。
2. **歷次巡檢共用同一個 context**——可跨次比較（「近三時段耗時 13 → 187 → 26 秒」不必回頭讀檔），但也因此持續累積，長時間運行會觸發 context 壓縮，故結論仍須落檔（§8）。
3. **Monitor 與 cron 的差異只在觸發層**。實際工作同樣由主 agent 在對話內做；`persistent: true` 的定義是「until TaskStop **or the session ends**」。**若卡住的原因是 session 結束，換 Monitor 沒有幫助。**

### 1.2 cron 的硬限制

| 限制 | 影響 | 對策 |
|---|---|---|
| Session-only，不寫入磁碟 | session 結束即消失 | 結論落檔（§8）；重開 session 要重建（§9） |
| 僅於 REPL idle 時觸發 | 執行中不會插入 | 實測影響很小（§10.1），不需為此改機制 |
| recurring 有 jitter | 最多晚「週期的 10%」，上限 15 分鐘 | 這是延遲的主因；要準時就用一次性任務或背景計時器 |
| 7 天後自動到期 | 跑最後一次後刪除 | 屆期前重新建立 |
| `durable` 參數無作用 | 工具定義明載 durable persistence is not available | 不要以為設了它就能持久化 |
| 一次性任務落在 `:00`／`:30` | 工具會讓它最多**提早** 90 秒觸發 | 避開整點與半點 |

## 2. 第一步：辨識執行環境

同一支 `claude` 執行檔有兩種啟動模式，session 內排程器的行為完全不同。

| 模式 | 啟動方式 | session 內排程器 |
|---|---|---|
| **終端機 TUI** | 使用者在終端機執行 `claude` 進入互動式 REPL | 正常。cron 會觸發；已有連續 40 個整點零缺口的實測（§10.1） |
| **VS Code 外掛（headless）** | 外掛以 `claude.exe --output-format stream-json --input-format stream-json --permission-prompt-tool stdio …` 啟動，經 stdin/stdout JSON 協定驅動 | 排程器有建立、也有 tick，**但從不觸發任務**。`CronCreate` 回成功、`CronList` 列得出、`ScheduleWakeup` 也建得成，然後永遠不響（§10.3） |

### 2.1 辨識法（任一成立即可判定為外掛模式）

1. 系統提示含「VSCode Extension Context」或「running within the Claude Agent SDK」字樣。
2. 查 `claude.exe` 行程的命令列（Windows 用 `Get-CimInstance Win32_Process`）含 `--input-format stream-json`。
3. 存在外掛日誌檔：`%APPDATA%/Code/logs/<啟動時間>/window*/exthost/Anthropic.claude-code/Claude VSCode.log`。

### 2.2 外掛內 cron 不會響的直接判據

外掛日誌中，排程器第一次看到任務會寫 `[ScheduledTasks] scheduled <id> for <time>`，觸發時寫 `firing <id>`。實測外掛 session 整段只有 `scheduler start()`、`tool_dispatch_end outcome=ok`、`acquired scheduler lock` 三類行，**從未出現 `scheduled … for`**——這一行缺席，就是排程器看不到任務。

成因（自二進位內 JS 還原，屬推測，未在執行期驗證）：session-only 任務清單與排程器計時器分屬不同上下文，工具呼叫讀寫的是一份、計時器讀到的是另一份空清單；TUI 模式下兩者同在根上下文故正常。此為外掛模式之缺陷，非設定問題，**不要試圖在 session 內修它**。

### 2.3 本步的判定與後果

| 判定 | 後果 |
|---|---|
| 終端機 TUI | cron 可用，但仍須經 §4.1 探針驗證後才依靠 |
| VS Code 外掛 | **不要建 cron，也不要用 `ScheduleWakeup`**；已建者用 `CronDelete` 清掉。改用背景計時器（§6.2）或 Monitor（§6.3） |

## 3. 第二步：依需求選機制

### 3.1 決策表

| 需求 | 終端機 TUI | VS Code 外掛 |
|---|---|---|
| 每隔 N 分鐘／小時**主動巡檢**一次 | `CronCreate`（recurring） | 背景計時器配方 C（§6.2） |
| 「N 分鐘後提醒我一次」「幾點以後才開始」 | `CronCreate` + `recurring: false`（準時，無 jitter） | 背景計時器配方 A |
| 做完 A、等一段時間、再做 B | 一次性 cron 串接 | 背景計時器配方 B（md 驅動） |
| 檔案／行程／指令輸出**一有變化就立刻知道** | `Monitor`（事件驅動） | `Monitor` |
| 永遠有紀錄、不依賴 session | 管線內建巡檢（§6.4） | 同左 |
| 視窗關了也要準時啟動 | 作業系統排程拉起 headless claude（§6.5，未實測） | 同左 |

### 3.2 取捨總表

| | cron | 背景計時器 | Monitor | 管線內建 | 作業系統排程 |
|---|---|---|---|---|---|
| 觸發來源 | 排程佇列（recurring 有 jitter） | 背景行程結束之完成通知（延遲 5～15 秒） | 背景行程推送 stdout | 管線自身收尾 | 系統排程器 |
| 可用環境 | 只有終端機 TUI | TUI 與外掛皆可 | TUI 與外掛皆可 | 不依賴 session | 不依賴 session |
| 需要 session 存活 | 是 | 是 | 是 | **否** | **否** |
| 能判讀與修復 | 是 | 是 | 是 | 否，只能機械檢查與落檔 | 否，只能依預寫規則 |
| 週期任務 | 內建 recurring，7 天到期 | 每次喚醒須重掛，不到期 | 迴圈內建 | 隨管線 | 內建 |
| 主動推送到使用者眼前 | 是 | 是 | 是 | 否，需自行查檔 | 否 |

**建議組合**：以管線內建巡檢保底（永遠有紀錄），再依環境擇一做即時推送與判讀——TUI 用 cron 或 Monitor，外掛用背景計時器或 Monitor。

### 3.3 什麼時候不該用 session 排程

session 排程的本質是**對話內的提醒**，不是可靠的常駐監控。它的獨特價值是能查證、判讀、改碼、驗證——回答「為什麼怪怪的」；作業系統排程只能回答「有沒有掛」。兩者互補：改動頻繁、需要判斷力的期間用 session 排程做深度巡檢；長期無人值守用作業系統排程或管線內建巡檢做存活告警。

## 4. 第三步：先驗證機制再依靠

**為什麼不能省**：cron 排入的 prompt 與使用者手動貼上的文字在對話內完全相同，單看任一則紀錄都無法斷定來源；「一直沒動靜」與「正常但沒事發生」在使用者眼裡也完全相同。曾有整整一天把「通知管道本身壞了」誤判為「管線壞了」而反覆修沒壞的東西（§10.2）。新環境、新版本、或懷疑機制時，先花兩到五分鐘做下面對應的驗證，結果與時間戳寫進 `./tmp/sched_test/`。

### 4.1 cron：一次性 nonce 探針（不動既有排程）

另建一個 `recurring: false` 的任務，prompt 內含一串自行生成、使用者從未見過的 nonce，要求把抵達時間寫入檔案：

```
CronCreate({
  cron: '<幾分鐘後的分> <時> <日> <月> *',
  recurring: false,
  prompt: 'PROBE-<nonce>：立刻把 "PROBE-<nonce> arrived at <本地時間>" 追加寫入 ./tmp/sched_test/cron-probe.txt，並回報與排定時間相差幾秒。',
})
```

nonce 出現＝機制成立，順帶量到實際延遲。既有巡檢任務不必刪除或重設。驗完刪掉探針檔。

### 4.2 背景計時器：兩分鐘協定

1. 背景執行 `sleep 60; node <小程式>` → 應在 60 秒後收到通知，且能自 `output-file` 讀到程式輸出。
2. 背景執行 `sleep 60` → 通知抵達後讀一份 md 並照做 → md 內要求再掛一個 `sleep 60` → 第二次通知後執行 B。
3. 同時對照 `CronCreate`（一次性、下一分鐘）與 `ScheduleWakeup(60)`：TUI 應觸發，外掛不會。

通過 1、2 才可把計時器當作正式排程。

### 4.3 Monitor：最小實驗

```
Monitor({
  description: '最小實驗：每分鐘推送一行，驗證能否定時喚醒',
  persistent: false, timeout_ms: 600000,
  command: 'n=0; while [ "$n" -lt 8 ]; do sleep 60; n=$((n+1)); echo "WAKE-TEST #${n} $(date +%H:%M:%S)"; done',
})
```

在使用者完全不發訊息的情況下，應每 60 秒收到一則通知並能對外回話。通過後再換成正式版。

### 4.4 事後查證：紀錄檔的時段覆蓋率

翻紀錄檔條目時間看有無缺口。關鍵在整夜那段——人不可能整夜每小時起來貼一次 prompt，連續的深夜條目即可判定為排程觸發。這是最弱但實務上最常用的證據。

## 5. 第四步：撰寫自足任務書

排程觸發時是獨立的一輪對話，讀不到「前面說過的內容」；背景計時器醒來時更是只有一則「計時器到期」通知。任務書（prompt 或 md 檔）必須自足，且包含下列六項。任務內容長、或 context 可能在等待期間被壓縮時，把任務書寫成檔案（例：`./tmp/<案名>/task.md`），醒來第一步就是讀它。

### 5.1 檢查對象的絕對路徑與識別名

日誌目錄、排程任務名稱、紀錄檔位置都寫死絕對值，不用「那個目錄」「上次那個任務」。**但每一個路徑都必須有明確來源，只有三種**：

| 來源 | 適用 | 取得方式 |
|---|---|---|
| 使用者指定 | 被巡檢對象的日誌位置、排程任務名、紀錄檔要放哪 | 使用者沒說就問，問的是具體那一項 |
| 被巡檢對象自身的設定或程式碼 | 日誌路徑樣式、輸出目錄 | 讀其設定檔或日誌初始化程式碼確認，任務書內附 `file:line` |
| AI 暫存慣例 `./tmp/` | 巡檢自己產生的東西：探針檔、任務書、機制證據、使用者未指定位置時的紀錄檔 | 直接用，回報時告知位置 |

**絕不自行發明專案內的路徑**（例如假設日誌在 `./log/`、把紀錄檔放在專案根目錄）：專案或套件本身可能正用同名目錄在運行，寫進去會覆蓋或混淆既有資料。任務書內的寫法：

```
- 日誌：<自管線設定取得之絕對路徑樣式>（來源：<設定檔或程式碼 file:line>）
- 作業系統排程：<使用者指定之排程任務名>（查詢指令寫全）
- 紀錄檔：<使用者指定之絕對路徑；未指定則 ./tmp/<案名>/監控運維紀錄.md>
```

### 5.2 可機械判定的正常／異常判準

不能寫「看起來正常」。範本：

> **正常** ＝ 該時段有日誌檔，**且**末段有「任務完成」標記，**且**有「已通知」標記，**且**排程離開碼為 0
> **異常** ＝ 上述任一不成立、日誌中有 ERROR、或**該跑的時段完全沒有產生日誌檔**

最後一條最容易漏、卻最重要：沒有日誌檔代表程式在建立日誌之前就崩潰了（相依套件缺失、語法錯誤），什麼線索都不會留下。判準要一併寫明處置：**手動執行一次以取得真實錯誤訊息**。曾有管線因全域相依被清除而在 import 階段崩潰，連失敗通知都發不出，靜默壞了六天才被發現——正是這條要抓的情形。

### 5.3 離開碼 0 不等於成功

管線若自行捕捉錯誤並優雅結束，作業系統看到的仍是正常退出（`LastTaskResult=0`）。曾有整批資料遺失、只發出「失敗」通知，離開碼仍為 0。**故不可只看排程狀態，必須讀日誌確認有成功標記。**

### 5.4 異常時的處置授權與界線

要給修復權限，否則巡檢只能告警而失去價值；但必須寫明界線：

```
- 先查證再動手，不憑猜測改動；技術細節不確定時實測或查證。
- 只做最小必要修改，不重構；處置優先選可逆的設定變更。
- 【絕不可改】列出會造成不可逆損害的項目，例如：
    不改去重鍵的計算方式（會使全部歷史資料被判為新資料而重推）
    不改資料庫／集合名稱（會指向空集合）
- 修完後實際執行一次驗證。
- 暫存檔一律放 ./tmp/，用完清掉。
```

「絕不可改」清單是最重要的部分——它把 AI 自主修復的爆炸半徑限制在可接受範圍。

### 5.5 結果寫入紀錄檔

見 §8。任務書內直接寫「用 Edit 追加到 `<紀錄檔>`，不要覆寫整份檔案」。

### 5.6 回報格式

正常時只回一行，異常時才展開，避免每小時洗版；並要求用**實際絕對時間**，不用「今天／剛才」——紀錄會被日後回讀，相對時間屆時無法解讀：

```
## YYYY-MM-DD HH:mm — 正常（耗時 {N}s，{產出量}）
```

## 6. 第五步：建立

### 6.1 cron（限終端機 TUI）

```
CronCreate({
  cron: '10 * * * *',      // 每小時 :10
  recurring: true,         // 一次性提醒用 false
  prompt: '<§5.7 之任務書>',
})
```

選時間點的兩個原則：

1. **錯開被巡檢管線的執行區間**——管線整點啟動、最壞跑 N 分鐘，巡檢就設在 N 分鐘之後。
2. **避開 `:00` 與 `:30`**——這兩點是所有人的預設值，全球請求同時打到 API；工具定義也建議挑非整點分鐘。

一次性任務把分／時／日／月都釘死（`'30 14 <日> <月> *'`，`recurring: false`），它沒有 recurring 的 jitter（實測誤差秒級），需要準時就用它。

### 6.2 背景 `sleep` 計時器（TUI 與外掛皆可）

原理：`run_in_background: true` 的行程結束時 harness 送通知叫醒主 agent；不受前景 timeout 約束（60 分鐘實測準時；同 session 曾有背景工作連跑 89 分鐘以上未被砍）。

**配方 A：一次性，指定牆鐘時刻**

```
Bash({ run_in_background: true, description: '計時到 <HH:MM> 後叫醒',
  command: 't=$(( $(date -d "<YYYY-MM-DD HH:MM:SS>" +%s) - $(date +%s) )); echo "armed at $(date +%H:%M:%S), wait ${t}s"; [ "$t" -gt 0 ] && sleep "$t"; echo "timer expired at $(date +%H:%M:%S)"' })
```

通知抵達後先 `date` 確認時刻，再讀任務書開始工作。

**配方 B：多步串接（md 驅動）**——第一個計時器到期 → 讀 `taskA.md` → 做 A → **立即再掛**第二個計時器 → 到期讀 `taskB.md` → 做 B。每段的 md 都要自足（§5 六項同樣適用）。

**配方 C：週期巡檢**——每次喚醒的最後一步是**重掛下一個計時器**（`sleep 3600`），並把「下次到期時刻」寫進紀錄檔。與 cron 的差異：沒有 jitter（延遲 5～15 秒）；不會自動到期；**忘記重掛就斷鏈**，任務書內必須明寫「完成後重掛」；仍綁 session。

**寫法要點**：

- 只用 `sleep`（Git Bash 可用），不用 `timeout` 指令；前景 `sleep` 會被工具政策擋下，一律 `run_in_background: true`。
- 命令內印出設定時刻與到期時刻，通知的 `output-file` 會帶回這兩行，可算延遲。
- 時刻用 `date -d "<絕對時刻>" +%s` 計算，不要心算秒數；`t ≤ 0` 時直接執行不 sleep。
- 一個計時器只做一件事；要「到期後跑程式」就接在 `sleep` 之後（`sleep N; node x.mjs`），通知即代表程式已跑完。
- 通知抵達時你可能正忙於其他 turn，通知會排隊不會遺失；但 session 結束就全部消失。

### 6.3 Monitor（TUI 與外掛皆可）

先做 §4.3 的最小實驗，通過後換正式版。**推薦事件驅動而非時間驅動**——監看巡檢紀錄檔的 mtime，一有更新即推送（那正代表管線剛跑完），並且**一定要有「太久沒更新」的告警分支**：

```bash
f='<紀錄檔絕對路徑>'
last=$(stat -c %Y "$f" 2>/dev/null || echo 0); warned=0
while true; do
  sleep 60
  cur=$(stat -c %Y "$f" 2>/dev/null || echo 0); now=$(date +%s)
  if [ "$cur" != "0" ] && [ "$cur" != "$last" ]; then
    last=$cur; warned=0
    echo "[巡檢] $(date +%H:%M) $(grep -m1 '^- 判定：' "$f")"
  elif [ "$cur" != "0" ] && [ $((now-cur)) -gt <週期秒數×1.25> ] && [ "$warned" = "0" ]; then
    warned=1
    echo "[告警] $(date +%H:%M) 紀錄檔已 $(( (now-cur)/60 )) 分鐘未更新——管線可能沒在跑"
  fi
done
```

那條 `elif` 不可省：只監看「有更新」的話，管線掛掉與一切安靜在使用者眼裡完全相同。Monitor 工具自己的說明也強調 *silence is not success*。`persistent: true` 仍綁 session。

### 6.4 管線內建巡檢（不依賴 session）

最可靠的保底：被監控的管線本來就週期執行，在它的收尾階段順手做機械檢查並更新紀錄檔，成本近乎零。

```js
// 管線主程式的 finally
} finally {
    lock.release()
    log.info(`管線結束，耗時 ${elapsed}s`)
    try {
        await patrolFromPipeline()   // 唯讀統計 + 追加紀錄檔
    }
    catch (err) {}                   // 巡檢自身失敗絕不可影響管線成敗
}
```

放在鎖釋放之後，且巡檢函式內部吞例外。語意最直接：**管線有跑 → 紀錄檔必被更新；紀錄檔長時間沒更新 → 管線沒在跑**。代價是只能機械檢查與落檔，判讀與修復仍要靠 cron／計時器／Monitor 把主 agent 叫醒。

### 6.5 跨 session：作業系統排程拉起 headless claude（未實測）

要「視窗關了也會啟動」，路線是：作業系統排程（Windows 為 `schtasks /SC ONCE /ST HH:MM`）拉起一支 detached 腳本，腳本以 headless 方式啟動 `claude -p <任務書>` 執行整個任務，輸出落 log。**此路線尚未實測**，用前先以 5 分鐘級測試驗證，並注意 LogonType 與彈視窗問題（見 `role-setup-scheduler-for-windows`）。

不建議的變體：用作業系統排程直接跑一支巡檢腳本。它與 §6.4 職責重疊，且 `InteractiveToken` 每次執行都會彈出 cmd 視窗、`Password` 需要密碼、`S4U` 需要額外權限；已做 §6.4 就不需要這條。

## 7. 巡檢執行要點

以下是實際運行數十次後才浮現的問題，任務書寫作與執行時都要對照。

### 7.1 檢查前先確認該時段是否已被檢查過

排程延遲會導致「使用者已提前手動問過、隨後排程才觸發」。此時應確認紀錄檔中該時段是否已存在條目，已存在就不要重複追加，避免污染紀錄。

### 7.2 觀察事項要有明確的升降級判準

不要讓「待觀察」無限累積：

- **升級**：出現具體後果或逼近門檻時（例：耗時達逾時上限的 80%）。
- **降級／結案**：連續 2～3 個時段回到正常區間即結案，並在紀錄中寫明「確認為單次波動，非趨勢」。

### 7.3 處置門檻要事先想清楚

「變慢」與「不通」是不同性質：單純變慢 → 不處置（若已有遞補機制且管線仍成功）；出現逾時且**重複多個時段** → 停用該來源（可逆的設定變更）。處置選**最小且可逆**的手段（例如加一行 `enable: false`），不動架構。

### 7.4 已知常態白名單須成套

管線每輪必然出現、且已有機制兜底的警告，一律不展開，只在紀錄中帶一句「WARN 均為已知情形」；須展開的限於**前所未見的錯誤字串**、管線未正常結束、有 ERROR。

**白名單漏列會讓自適應機制卡死**：曾有巡檢只列了某類失敗中見過的幾個變體、漏了同級的另一個，導致同一個死來源連續三輪被判為「未知警告」，巡檢頻率因此永遠停在最密的一檔爬不上去。**同一種失敗的各個變體要一起列**，不能只列見過的那幾個。建議按層分類並註明兜底來源，日後新增兜底機制時同步維護：

```
抓取層（有重試／雙來源兜底）：HTTP 4xx 各碼｜連線層錯誤（逾時、拒絕、DNS）｜驗證碼｜導向｜內容過短
處理層（有部分接受／換家兜底）：輸出驗證失敗｜逾時
正常運作訊息（設計如此，非異常）：略過項目｜本批採用 N 篇｜留待下輪｜自動停用
```

### 7.5 同類訊息要正規化後去重

同一則訊息會逐輪重複出現（如同一個死來源每輪重抓），逐筆列出會洗版並淹掉真正的新問題。先去掉標題、數字等隨輪次變動的部分再去重，只報「不同種類」並附出現次數：

```
[×3] 04:00 fetch: WARN 全文[…] 失敗（連線層錯誤…）
```

## 8. 紀錄檔

**理由**：session 隨時可能結束，屆時對話內的巡檢結論一併消失；落檔後即使排程失效、session 重開，歷史與待觀察事項仍在，新 session 可直接接續。以**追加**方式寫入，任務書內明確要求「用 Edit 追加，不要覆寫整份檔案」。

**位置**：由使用者指定；未指定時放 `./tmp/<案名>/`，並在第一次回報時告知路徑。不得自行放進專案既有目錄或根目錄（§5.1）——那是專案自己的空間，巡檢是外掛在旁邊的東西。

| 情況 | 記法 |
|---|---|
| 正常 | 一行：時間、耗時、產出量 |
| 正常但有值得留意的現象 | 一行 ＋ 簡短註記（例：某來源耗時逼近上限） |
| 異常 | 一節：**現象 → 根因（附證據）→ 處置 → 驗證結果** |
| 做了改動 | 變更表（哪個檔、改什麼、為什麼），含實測數據 |
| 背景計時器模式 | 另記「下次到期時刻」 |

**根因務必附證據**：`file:line`、實際錯誤訊息、或實測數列。只寫「疑似服務不穩」對日後毫無幫助。

**也要記「決定不處理」及其理由**，與記錄問題同等重要：

> 某來源回應時間波動（12～139 秒），但全部遠低於逾時上限、產出每次皆完整。維持觀察不處置——真正需處置的判準是「出現逾時或連續驗證失敗」，單純變慢不構成損失。

否則下一輪巡檢或另一個 session 會重新糾結同一件事，甚至為消除假想風險而引入真實退化。

**附帶價值**：紀錄檔本身就是排程存活的證據（§4.4）。

**長時間沒有巡檢回報時的排查順序**：

3. 紀錄檔覆蓋率（§4.4）——最後一筆是幾點？
4. 重做一次探針或最小實驗（§4）——機制本身還通嗎？
5. 以上都正常，才去查被巡檢的管線。
