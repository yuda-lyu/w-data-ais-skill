# role-setup-scheduler-for-session — Session 內定時巡檢設定要點

## 概述

把「定時檢查某個排程管線是否正常，異常就診斷並修復」交給 Claude session 自身的排程執行。

核心來自兩個專案的實測：`c:/tai-news` **運作 20+ 次巡檢**歸納的做法，以及 `c:/tai-kns-trade` 於 2026-08-10 的**反例**（該專案 cron 一整天完全打不通，最後改用 Monitor 與「管線內建巡檢」才解決——見 §2.1、§8）。

- **適用**：管線改動頻繁、需要判斷力的巡檢期間
- **不適用**：長期無人值守的存活告警（見 §7）

> **與作業系統排程的分工**：作業系統排程（見 `role-setup-scheduler-for-windows`）只能依預寫規則告警；session 排程的獨特價值是**能查證、判讀、改碼、驗證**——即「為什麼怪怪的」而非只是「有沒有掛」。

## 何時使用此 Skill

- 要讓 Claude 每隔一段時間自動檢查某條管線是否正常
- 巡檢發現異常時要能自主診斷並修復
- 要撰寫巡檢用的自足 prompt
- **cron 建了卻沒反應，要查證機制本身通不通**

---

## 1. 執行模型：cron 排的是 prompt，不是任務

**`CronCreate` 把一段 prompt 排入「本對話」的佇列，時間到即以一則普通 user message 送進來，由主 agent 在自己的 context 內執行。不會另外 spawn agent，也沒有回報管道。**

依據為工具契約本身：定義是「Schedule a prompt to be **enqueued** at a future time」，其 `prompt` 參數為「The prompt to **enqueue** at each fire time」。

三個推論，都影響設計：

1. **prompt 必須自足**——它是新一輪對話的開場，讀不到先前脈絡（§4）。
2. **歷次巡檢共用同一個 context**——可跨次比較（「近三時段耗時 13 → 187 → 26 秒」不必回頭讀檔），但也因此持續累積，長時間運行會觸發 context 壓縮。
3. **與 Monitor 的差異只在觸發層**。Monitor 是背景進程推送 stdout 成為通知，不受 idle 阻擋；但實際工作同樣由主 agent 在對話內做，且 `persistent: true` 的定義是「until TaskStop **or the session ends**」——**session 綁定這一項兩者完全相同**。若卡住的原因是 session 結束或到期，換 Monitor 不會有幫助。

### 硬限制

| 限制 | 影響 | 對策 |
|---|---|---|
| **Session-only**，不寫入磁碟 | session 結束即消失 | 結果必須落檔（§5）；重開 session 要重建 |
| **僅於 REPL idle 時觸發** | 正在執行中不會插入 | **實測影響很小**（見下） |
| **recurring 有 jitter** | 最多晚「週期的 10%」，上限 15 分 | 這是延遲的**主因**；要準時就別用 recurring |
| **7 天後自動到期** | 跑最後一次後刪除 | 屆期前需重新建立 |

> ⚠ **`durable` 參數沒有作用**——工具定義明載「durable persistence is not available，All jobs are session-only」。**不要以為設了它就能持久化。**

### 實測：延遲的主因是 jitter，不是等 idle（2026-08-10）

| 任務 | 排定 | 實際抵達 | 誤差 |
|---|---|---|---|
| 每小時 recurring（`10 * * * *`） | `:10` | `:26`／`:29`／`:26`／`:26` | **晚 16~19 分** |
| 一次性 probe（`recurring: false`） | `15:57` | `15:57:06` | **晚 6 秒** |

兩者跑在同一個 session、同一段時間內，差別只有 `recurring` 之有無。故延遲來自 **recurring 的 10% jitter**（每小時任務即最多 6 分鐘），而非對話忙碌。

> **先前的錯誤推論已更正**：舊版說法為「`:26` 是因為前面幾輪在跑端到端驗證而佔用對話」，該說法未經查證。probe 於使用者剛輸入完、REPL 才空出數十秒即抵達，證明 **idle 阻擋的實際成本很小**。
>
> 註：jitter 上限（每小時 6 分）仍不足以解釋全部的 16~19 分，**殘差成因未查證**；但已可確定「錯開對話忙碌區間」不是有效對策。

**實務結論**：巡檢工作是「回頭讀一份已寫好的日誌」，日誌不會消失，晚 16 分鐘讀到的內容完全相同，故 **jitter 無害、不需要為此改用 Monitor**。只有「需在事件發生當下介入」或「延遲須壓在秒級」才值得換機制。

> one-shot 任務若落在 `:00` 或 `:30`，工具會讓它**最多提早 90 秒**觸發（與 recurring 的延後相反）。

## 2. 先確認該用哪個工具

| 需求 | 該用 | 理由 |
|---|---|---|
| 每隔 N 分鐘／小時**主動巡檢**一次 | **`CronCreate`** | 固定牆鐘週期重跑 prompt |
| 要在檔案／行程／指令輸出**一有變化就立刻知道** | **`Monitor`** | 串流事件、即時觸發；cron 是輪詢 |
| 長期無人值守的存活告警 | **作業系統排程**或**管線內建巡檢**（§8.2） | session 不會一直開著 |
| 「N 分鐘後提醒我一次」 | `CronCreate` + `recurring: false` | 觸發一次後自動刪除 |

### 2.1 反例：cron 在某些 session 會完全不送達（tai-kns-trade，2026-08-10）

同一台機器、同樣是 VSCode plugin、session 同樣未斷，但該專案的 cron **一整天未曾送達使用者眼前**。四次建立任務的觀測：

| 時段 | 主 agent 當時狀態 | 結果 |
|---|---|---|
| 01:15~06:15（六次） | 持續跑 10~30 分鐘的背景驗證任務 | 未見任何巡檢 |
| 08:25 | 正在寫任務歷史（工具調用連續） | 未見 |
| 14:2x | 正在改碼 | **確實送達**——prompt 已排入對話，隨即被使用者中斷 |
| 15:25 | **完全靜默 45 分鐘**（使用者亦未發訊息） | **未見** |

最後一列與 §1 的結論**直接衝突**：既然 idle 阻擋成本很小、jitter 每小時最多 6 分鐘，`15:25 + 6 分 = 15:31` 就該抵達，但直到 15:42 都沒有。

> **兩邊數據都是實測，差異成因未查明，不宜編故事解釋**。該專案先前已為此推論錯兩次（先誤判「機制不可靠」、再誤判「對話太忙被順延」），兩次都導向錯誤的處置。

可確定的只有一件事：**cron 在某些 session 會完全不送達，且無法從 session 內診斷原因**（`CronList` 只證明任務註冊在案，不透露上次／下次觸發時間）。

**故 §6 的查證手段必須前置執行**：新建 cron 後，先用 §6.3 的 nonce 探針確認機制真的通，再把它當成監控依靠。tai-kns-trade 的教訓是連續一整天以為「排程壞了要修管線」，實際上壞的是通知管道本身。

## 3. 建立

```
CronCreate({
  cron: '10 * * * *',      // 每小時 :10
  recurring: true,         // 預設 true；一次性提醒用 false
  prompt: '（完整巡檢指令，見 §4）',
})
```

**選時間點的兩個原則**：

1. **錯開被巡檢管線的執行區間**——管線整點啟動、實測 1~5 分鐘內結束，故巡檢設 `:10`。若管線最壞要跑 14 分鐘，就設 `:15` 以後。
2. **避開 `:00` 與 `:30`**——這兩點是所有人的預設值，全球請求會同時打到 API。工具定義也明確建議挑非整點分鐘（如 `7 * * * *` 而非 `0 * * * *`）。

### 一次性任務（`recurring: false`）

用於「某時做一件事」而非週期巡檢。須把分／時／日／月都釘死：

```
CronCreate({
  cron: '30 14 <日> <月> *',
  recurring: false,
  prompt: '檢查今日部署是否完成',
})
```

> 一次性任務**沒有 recurring 的 10% jitter**（實測誤差僅 6 秒），需要準時就用它。

## 4. prompt 的撰寫要點

排程觸發時是**獨立的一輪對話**，讀不到「前面說過的內容」。prompt 必須自足，且包含下列六項：

### 4.1 檢查對象的絕對路徑與識別名

日誌目錄、排程任務名稱都要寫死絕對值：

- 日誌：`c:/tai-news/log/{今日}/{YYYYMMDDHHmmss}.log`
- 排程：`Get-ScheduledTask -TaskName 'trigger-news-ai' | Get-ScheduledTaskInfo`

### 4.2 明確的正常／異常判準（必須可機械判定）

不能寫「看起來正常」。tai-news 用的是：

> **正常** ＝ 日誌末行有「任務完成」，**且**出現「已發送 Telegram」或「已通知」，**且** `LastTaskResult=0`
> **異常** ＝ 上述任一不成立、日誌中有 ERROR、或**該跑的時段完全沒有產生日誌檔**

**最後一條最容易漏掉，卻最重要**：沒有日誌檔代表程式在「建立日誌之前」就崩潰了（相依套件缺失、語法錯誤），此時什麼線索都不會留下。判準要一併寫明處置方式：**手動執行一次以取得真實錯誤訊息**。

> **實測價值**：tai-news 曾因全域相依被清除而在 import 階段崩潰，連失敗通知都發不出，**靜默壞了 6 天**才被發現——正是這條判準要抓的情形。

### 4.3 關鍵陷阱：`LastTaskResult=0` 不等於成功

管線若**自行捕捉錯誤並優雅結束**，作業系統看到的仍是「正常退出」。tai-news 就發生過：整批新聞遺失、只發出「選文失敗」通知，但 `LastTaskResult` 仍為 0。

**故不可只看排程狀態，必須讀日誌確認有成功標記。**

### 4.4 異常時的處置授權與界線

要給修復權限，否則巡檢只能告警而失去價值。但必須寫明界線：

```
- 先查證再動手，不要憑猜測改動；技術細節不確定時實測或查證。
- 只做最小必要修改，不重構。
- 【絕不可改】列出會造成不可逆損害的項目。
  例：不改去重鍵 sha1(url.trim())（會使 52k+ 筆舊資料全部重推）、
      不改資料庫 db／cl 名稱（會指向空集合）。
- 修完後實際執行一次驗證。
- 暫存檔一律放 ./tmp/，用完清掉。
```

> **「絕不可改」清單是最重要的部分**——它把「AI 自主修復」的爆炸半徑限制在可接受範圍內。

### 4.5 結果寫入檔案

見 §5。

### 4.6 回報格式

正常時只回一行，避免每小時洗版；異常時才展開。prompt 內直接指定格式：

```
## YYYY-MM-DD HH:mm — 正常（{耗時}s，{N}/{M} 篇有摘要）
```

並要求**用實際絕對時間，不要用「今天／剛才」等相對詞**——巡檢紀錄會被日後回讀，相對時間屆時無法解讀。

## 5. 結果必須落檔

**理由**：session 隨時可能結束，屆時對話內的所有巡檢結論一併消失。落檔後即使排程失效、session 重開，歷史與待觀察事項仍在，新 session 可直接接續。

tai-news 寫入 `./監控運維紀錄.md`，以**追加**方式（明確要求「用 Edit 追加，不要覆寫整份檔案」）。

### 檔案該記什麼

| 情況 | 記法 |
|---|---|
| 正常 | 一行：時間、耗時、產出量 |
| 正常但有值得留意的現象 | 一行 ＋ 簡短註記（例：某供應商耗時逼近上限） |
| 異常 | 一節：**現象 → 根因（附證據）→ 處置 → 驗證結果** |
| 做了改動 | 變更表（哪個檔、改什麼、為什麼），含**實測數據** |

**根因務必附證據**：`file:line`、實際錯誤訊息、或實測數列。只寫「疑似服務不穩」對日後毫無幫助。

### 也要記「決定不處理」及其理由

這點與記錄問題同等重要。例：

> deepseek 回應時間波動（12~139s），但全部遠低於 300s 逾時上限、摘要每次皆完整產出。
> 維持觀察不處置——真正需處置的判準是「出現逾時或連續驗證失敗」，單純變慢不構成損失。

否則下一輪巡檢（或另一個 session）會重新糾結同一件事，甚至為了消除假想風險而引入真實退化。

> **附帶價值**：紀錄檔本身就是**排程存活的證據**（見 §6.2）。

## 6. 如何查證「cron 真的有在跑」

這件事比想像中不直觀，因為**cron 排入的 prompt 與使用者手動貼上的文字，在 transcript 內完全相同、沒有任何來源標記**。單看任何一則巡檢紀錄，都無法斷定其來源。

三種查證手段，強度由弱到強：

### 6.1 `CronList`（弱）

只證明任務仍註冊在案，不證明它會觸發，也查不到其他 session 的任務。但「長時間沒有回報」時**第一件事仍是 `CronList`**——先確認任務還在，再去查被巡檢的管線。

### 6.2 紀錄檔的時段覆蓋率（中，但實務上已足夠）

翻紀錄檔的條目時間，看有無缺口。tai-news 實測：**`08-09 00:00` ~ `08-10 15:00` 連續 40 個整點，零缺口。**

關鍵在**整夜那段**（00:00 ~ 07:00 連續八個時段皆有完整條目）——人不可能整夜每小時起來貼一次 prompt，故可判定為 cron 觸發。

### 6.3 一次性 nonce 探針（強，且不必動既有排程）

要單次直接證據時，另建一個 `recurring: false` 的任務，prompt 內含一串**自行生成、使用者從未見過的 nonce**，並要求把抵達時間寫入檔案：

```
CronCreate({
  cron: '57 15 10 8 *',        // 幾分鐘後的一次性時點
  recurring: false,
  prompt: 'PROBE-<nonce>：立刻把 "PROBE-<nonce> arrived at <台北時間>" 追加寫入 ./tmp/cron-probe.txt，並回報與排定時間相差幾秒。',
})
```

nonce 自己出現＝機制成立。**既有的巡檢任務完全不需要刪除或重設**，不會中斷正在進行的監控。驗完刪掉 `./tmp/cron-probe.txt` 即可。

順帶可量到 jitter 的實際大小（§1 的兩組數據即由此得出）。

> **新建任何推送機制後，一律先做這一步再拿它當監控依靠**——否則會像 tai-kns-trade 那樣，花一整天在修沒壞的管線。

## 7. 巡檢時的實務要點

以下是實際跑了 20+ 次後才浮現的問題：

### 7.1 檢查前先確認該時段是否已被檢查過

排程延遲會導致「使用者已提前手動問過、隨後排程才觸發」。tai-news 發生過：21:23 使用者提問時已檢查完 21:00，21:26 排程才到——此時應**確認紀錄檔中該時段是否已存在**，若已存在就不要重複追加，避免污染紀錄。

### 7.2 觀察事項要有明確的升降級判準

不要讓「待觀察」無限累積：

- **升級**：出現具體後果或逼近門檻時（例：耗時達逾時上限的 80%）
- **降級／結案**：連續 2~3 個時段回到正常區間即結案，並在紀錄中寫明「確認為單次波動，非趨勢」

### 7.3 處置門檻要事先想清楚

「服務變慢」與「服務不通」是不同性質：

> 單純變慢 → 不處置（遞補機制已涵蓋，管線仍成功送出）
> 出現逾時且**重複多個時段** → 停用該供應商（可逆的設定變更）

且處置要選**最小且可逆**的手段（加一行 `enable: false`），而非改動架構。

### 7.4 設「已知常態不回報」白名單

管線每輪必然出現的、已有機制兜底的警告，一律不展開說明，只在紀錄中帶一句「WARN 均為已知情形」。否則雜訊會淹沒真問題。

須展開的限於：**前所未見的錯誤字串**、管線未正常結束、有 ERROR。

**⚠ 白名單漏列會讓自適應機制卡死**：tai-kns-trade 的巡檢原本漏列 `curl-error`（只列了同級的 `http-error`／`blocked`／`redirect`），導致同一個死網址連續三輪被判為「未知警告」，**巡檢頻率因此永遠停在最密的 1 分鐘而爬不上去**。

> **分類要成套補齊**——同一種失敗的各個變體要一起列，不能只列見過的那幾個。

白名單建議**分類註明來源**（日後新增兜底機制時須同步維護）：

```
抓取層（有 curl／雙供應商／重試兜底）：
  platform wrapper｜captcha｜HTTP 401·403·404·410·429｜minimal visible text
  curl-error｜http-error｜（blocked：｜（redirect：｜網格雙供應商皆失敗｜找不到 feed
AI 層（有部分接受＋截斷搶救＋換家兜底）：
  OUTPUT_VALIDATION_FAILED｜TIMEOUT after
正常運作訊息（設計如此，非異常）：
  略過非量化知識｜本批 N 篇採用｜未涵蓋者留待下輪｜自動停用｜預篩｜改用 feed 內文
```

### 7.5 同類訊息要正規化後去重

**同一則訊息會逐輪重複出現**（如同一個死網址每輪重抓），逐筆列出會洗版並淹掉真正的新問題。

做法：先正規化（去掉標題、數字等隨輪次變動的部分）再去重，只報「不同種類」並附出現次數：

```
[×3] 04:00fetch: WARN 全文[…] 失敗（curl-error…）
```

## 8. cron 打不通時的兩條備援

§2.1 的情形發生時（cron 完全不送達且無法診斷），以下兩條路實測可行。**兩者可並用**：B 是保底、A 是即時推送。

### 8.1 備援 A：Monitor 主動推送

`Monitor` 與 cron 的差異只在觸發層——它是**背景進程把 stdout 每一行變成通知**，不需要任何 turn 來驅動。tai-kns-trade 實測：`WAKE-TEST #1 15:50:38`、`#2 15:51:38`，在使用者完全未發訊息的情況下，間隔精準 60 秒連續喚醒主 agent 並成功對外回話。

**先做最小實驗再上正式版**（這步不可省，否則又是拿複雜設定去賭機制）：

```
Monitor({
  description: '最小實驗：每分鐘推送一行，驗證能否定時喚醒',
  persistent: false, timeout_ms: 600000,
  command: 'n=0; while [ "$n" -lt 8 ]; do sleep 60; n=$((n+1)); echo "WAKE-TEST #${n} $(date +%H:%M:%S)"; done',
})
```

驗證通過後換成正式版。**推薦事件驅動而非時間驅動**——監看「巡檢紀錄檔的 mtime」，一有更新即推送，因為那正代表管線剛跑完：

```bash
f='c:/專案/監控運維紀錄.md'
last=$(stat -c %Y "$f" 2>/dev/null || echo 0); warned=0
while true; do
  sleep 60
  cur=$(stat -c %Y "$f" 2>/dev/null || echo 0); now=$(date +%s)
  if [ "$cur" != "0" ] && [ "$cur" != "$last" ]; then
    last=$cur; warned=0
    echo "[巡檢] $(date +%H:%M) $(grep -m1 '^- 判定：' "$f")"
  elif [ "$cur" != "0" ] && [ $((now-cur)) -gt 4500 ] && [ "$warned" = "0" ]; then
    warned=1
    echo "[告警] $(date +%H:%M) 紀錄檔已 $(( (now-cur)/60 )) 分鐘未更新——管線可能沒在跑"
  fi
done
```

**那條 `elif` 告警分支是關鍵，不可省**：只監看「有更新」的話，管線掛掉與一切安靜在使用者眼裡完全相同——**沉默不等於正常**（Monitor 工具本身的說明也特別強調 *silence is not success*）。

> **限制**：`persistent: true` 的定義是「until TaskStop **or the session ends**」，故 session 綁定這點與 cron 完全相同。換 Monitor **不解決「session 結束」的問題**——那要靠備援 B。

### 8.2 備援 B：把巡檢掛進管線自己的收尾

最可靠的一條，因為它**完全不依賴 session 也不需要任何額外排程**：

```js
// trigger-*.mjs 的 finally
} finally {
  lock.release();
  log.info(`管線結束，耗時 ${log.elapsed()}s`);
  if (await patrolFromPipeline()) log.info('巡檢：已更新 監控運維紀錄.md');
}
```

管線本來就每小時執行，收尾時順手巡檢，成本近乎零（唯讀統計數秒）。放在 `lock.release()` 之後、且**巡檢函式內部吞例外——巡檢自身失敗絕不可影響管線成敗**。

語意也更直接：**管線有跑 → 紀錄檔必被更新；紀錄檔長時間沒更新 → 管線沒在跑**，而後者正是最該告警的事。tai-kns-trade 實測：`抓取管線結束，耗時 1194.9s` 之後緊接 `巡檢：已更新 監控運維紀錄.md`，檔案 mtime 與管線結束同秒。

代價是「只能機械檢查與落檔，不能判讀與修復」——判讀仍要靠 A 或 cron 把主 agent 叫醒。

### 8.3 一條不建議的路：獨立的作業系統排程跑巡檢腳本

看似最可靠，實測有惱人副作用（Windows）：

| LogonType | 需密碼 | 副作用 |
|---|---|---|
| `InteractiveToken` | 否 | **每次執行都跳 cmd 視窗**，`<Hidden>true</Hidden>` 擋不住（跑在使用者桌面 session）。巡檢若設每分鐘更是災難 |
| `Password` | **是** | 無視窗（跑在非互動 session）。但安裝腳本不應接收密碼——用 `/rp *` 讓 schtasks 自行詢問 |
| `S4U` | 否 | 無視窗，但該次實測建立失敗（存取被拒，需額外的批次登入權限） |

且它與備援 B 職責重疊卻更麻煩。**若已做了 B，就不需要這條。**

> ⚠ **若必須動既有排程，改完務必回查 `LogonType`**——`schtasks /create /f` 會刪除並重建任務，把使用者原本設好的 `Password` 打回 `InteractiveToken`，於是視窗又跳回來。
>
> LogonType 的完整說明見 `role-setup-scheduler-for-windows`。

## 9. 三個機制的取捨總表

| | cron | Monitor | 管線內建（§8.2） |
|---|---|---|---|
| 觸發來源 | 排程佇列（有 jitter；某些 session 完全不送達） | 背景進程推送 stdout | 管線自身收尾 |
| 需要 session 存活 | ✅ | ✅ | ❌ **不需要** |
| 能判讀與修復 | ✅ | ✅ | ❌ 只能機械檢查與落檔 |
| 主動推送到使用者眼前 | ✅ | ✅ | ❌ 需自行查檔 |
| 跳視窗／需密碼 | 無 | 無 | 無 |

**建議組合**：以 §8.2 保底（永遠有紀錄），再擇一用 cron 或 Monitor 做即時推送與判讀。

> 新建任一推送機制後，**一律先用 §6.3 的 nonce 探針或 §8.1 的最小實驗驗證機制真的通**，再拿它當監控依靠。

## 10. 什麼時候不該用這個做法

Session 排程的本質是**對話內的提醒**，不是可靠的常駐監控。

| 面向 | Session 排程（`CronCreate`） | 作業系統排程 |
|---|---|---|
| 存活 | session 結束即消失 | 持續存在 |
| 到期 | 7 天 | 無 |
| 觸發精度 | recurring 有 jitter；某些 session 不送達 | 準時 |
| 能否**診斷與修復** | ✅ 可（查證、判讀、改碼、驗證） | ❌ 只能依預寫規則告警 |
| 適用 | 改動期間盯穩定性 | 長期無人值守 |

**兩者互補**：長期用作業系統排程（或 §8.2 管線內建）做「有沒有掛」的告警；改動頻繁的期間用 session 排程做「為什麼怪怪的」的深度巡檢。

## 11. 維護

```
CronList()            // 確認任務仍在（只列得出本 session 的任務）
CronDelete({ id })    // 取消任務（id 由 CronCreate 回傳）
```

- **每次重開 session 都要重建**——目前無法規避（`durable` 無效）。
- 若長時間沒有巡檢回報，**第一件事是 `CronList`**，而不是去查被巡檢的管線。
- `CronList` **無法查證其他 session 的排程狀態**，也不透露上次／下次觸發時間。
- 7 天到期前若仍需要，需重新建立。
