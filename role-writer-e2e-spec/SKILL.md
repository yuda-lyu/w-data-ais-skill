# e2e 流程 spec 撰寫規範

**觸發條件**：凡寫、改、審 e2e 流程 spec 之任務，本篇整篇入 context 逐項比對後才動工。

**閱讀順序**：§0～§14 → `references/case-format.md`（三點結構逐欄格式、視覺序列、六問與掃描、對照表欄位、副作用清理表）→ `references/gap-classification.md`（已知落差之判定樹、缺陷歸屬分層、刻意設計六形態、典型誤判、修復紀錄、證據落點）→ `references/permission-and-accounts.md`（權限軸盤點、帳號矩陣、資料主從、權限與入口繞過案例）→ `references/lifecycle-rewrite-reconcile.md`（從零撰寫、改寫舊草稿、產圖後對帳、升版與修復後改寫三件事、不可自動化判準、派工守則）→ `references/shared-conventions.md`（共用文件章節、裁決紀錄格式、上游套件事項歸屬表、變更紀錄）。專案已有 spec 者，先讀既有 spec 與共用文件對齊風格，不從零自創。

**輕重緩急**（整批被退的原因一律出自這六件，動筆前先確認）：

1. **評斷任何行為之前先讀該層原始碼與定義**：共用元件之呈現、套件之功能、部署之授權，各有各的原始碼、prop 預設值、示範頁與設定項；沒讀就下「缺陷」「不對稱」「應改用 X」之結論，是本技能被退最多次的原因。全域或專案之 UI 規範管的是自製元件，不能反推共用元件為錯。
2. **事實只來自現行程式碼、產物與實機；「已修復」只認全新頁面之實測**；數字皆實測；草稿、舊文件、程式碼 diff 之推導都只是假設。
3. description 寫給使用者、六問齊全、能逐字進手冊表格。
4. 視覺項每步兩張、括號寫到元素、有中間狀態之元件拆兩步、產圖後與圖對過帳。
5. 權限分軸（畫面軸／資料軸／進入軸）、資料分主從；每個權限案例標軸別與帳號；帳號組合不存在就廢止保留編號，不硬寫。
6. 已知落差先分層歸屬、先查裁決，再分四類；「待裁示」只放業主不決定就無法往下做的事；回報一次、四類分開，不分段。

## 0. 定位：一份 spec，三種讀者，一個真理源

| 讀者 | 讀哪裡 | 要什麼 |
|---|---|---|
| 系統使用者（將來的手冊讀者） | 案例之 `title`、`description` | 在哪裡、怎麼做、會看到什麼、什麼時候用；畫面文字逐字 |
| e2e 實作者 | 案例之 `flow`、〈畫面元素對照〉、〈訊息對照〉、〈信件對照〉、〈規則摘要〉、〈已知落差〉 | 契約等級的操作與觀察、具名測試資料、`檔案:函式`、可達性與可自動化性證據、元件之可觀察性 |
| 手冊產製程式 | `head`（E2E-NNN）、`title`、`description`、視覺段之圖鍵 | 結構穩定、可機械解析、title 全冊唯一、無會被自動編號吃掉的佔位 |

- **spec 是真理，測試與手冊是它的翻譯**：測試 assertion 對應 spec 的句子；手冊的項目表逐字取自 spec。spec 沒寫具體的，回來補 spec，不在測試或手冊端各自發明。
- **事實來源只有現行程式碼、產物與實機行為**：「現行程式碼」包含專案自有碼、部署層接線、上游套件與共用元件庫之原始碼（`node_modules` 內）；前端由套件產物供應者，產物（`dist`）是否已含改動也是事實之一。舊版說明文件、需求書、架構文件、上一版草稿都不是依據，也不得拿來與現況比對後寫成落差。
- **spec 隨產品修復而改寫並留痕**：產品端修了缺陷，受影響案例改寫成新行為，舊行為留在〈已知落差〉附修復紀錄；spec 永遠描述現況。
- 三種讀者的內容**不可混寫**：description 出現 `檔案:函式`、案例編號、截圖階段、待實測標記＝寫給錯的讀者；flow 缺具名資料與觀察終態＝實作者無法落地。

## 1. 動工前盤查（缺一不可，寫進回報）

1. 讀專案跨流程共用文件（設計要點與取捨、標準圖命名、資料庫重置、測試帳號矩陣、資料主從、**裁決紀錄**、description 風格）與至少一份既有 spec，對齊章節與用語。
2. 讀該功能之程式碼入口：選單定義、頁面元件、各按鈕之條件渲染與權限條件、訊息文字定義處、進入前是否需捲動主選單，取得 `檔案:函式`。
3. **讀共用元件庫與上游套件之原始碼**：頁面用到的下拉、彈出層、表格、日期選擇器、抽屜等共用元件，先找到其原始碼、prop 預設值與示範頁；頁面由上游套件供應者，同時確認套件版本與產物是否為現行版本。這是評斷任何呈現行為之前提，不是遇到問題才做。
4. **實機探測**：以真瀏覽器走一遍每條路徑，記下畫面實際文字（含全形半形、空格、括號）、筆數、版次數、視窗寬度門檻、是否可點、訊息之樣式（右上提示或對話框）與時機（出現在什麼事件之後、停留多久）、元件之可觀察性（清單是否在 DOM 內）；探測 log 落專案內之證據目錄，引用時附檔名與段落。
5. **權限模型與資料主從盤點**（有權限樹或多系統共享資料者必做）：列出幾個軸（畫面、資料、進入、操作）、各軸鍵的形狀、資料軸依資料表類別各是什麼規則、種子帳號矩陣（哪個帳號能服務哪類負向案例）；多系統共享資料時列主從表（誰是真理源、同步方式與週期、次系統可否編修）；作法見 `references/permission-and-accounts.md` §1～§3、§6。
6. **可自動化性判準**：檔案選擇之取消、作業系統層對話框、剪貼簿拒絕、二進位單一端點之選擇性攔截、作業系統繪製之下拉清單等，先實測能否由測試框架造出；不能者不設案例或只設可拍之步驟（§4 第 10 條）。
7. 列出具名測試對象並複驗它們在現行資料庫確實存在（資料庫重建後須再複驗一次）；內建之「測試範例」對現行種子命中為零者，另選會命中之具名輸入，並把零命中記入〈已知落差〉。
8. **姊妹系統先例**：同組織之姊妹系統若已有同型元件之案例序列（統計頁下拉、關聯對話框、抽屜收合），以先完成者為範本對齊序列與圖數；差異須有理由並寫在備註。
9. 確認下游約束：手冊 lint 之禁詞與括號長度、title 唯一性、標準圖檔名前綴與 flow 代號登記；有專案 lint 就先對 title／description 跑一遍。

## 2. 三種任務型態（先判型態，再套流程）

| 型態 | 起點 | 核心紀律 | 流程細節 |
|---|---|---|---|
| 從零撰寫 | 無 spec | 由系統列舉（分頁 × 區塊 × 每區塊之按鈕／勾選／連結／輸入 × 訊息）→ 探測 → 姊妹先例 → 決定表 → 寫；具名輸入選會命中且結果最豐富者 | reference §1 |
| 改寫舊格式草稿 | 有草稿但早於現行通則 | **草稿每一句都是假設**：逐句標「已實測／未實測／實作猜測」，未實測者重探測、實作猜測（須遮罩、填黑、參數為 X）刪除、〈已知落差〉逐條重走判定樹；編號保留；description 已是手冊體者只補六問不重寫風格 | reference §2 |
| 回頭修 | 實作、產圖、手冊撰寫、套件升版或產品修復發現不符 | 升版／修復者先做三件事（全量 diff、確認產物、全新頁面實測），再改該句＋〈已知落差〉留痕＋同步測試檔與手冊內容檔＋只重產受影響之圖 | reference §3～§4 |

## 3. 文件骨架（一份 spec 的章節與各章責任）

| 章 | 內容 | `檔案:函式` |
|---|---|---|
| 標題與〈觸發〉 | 使用者從哪裡進入（含「主選單此項是否在可視範圍外，須先捲動」）；本文件涵蓋哪類流程（瀏覽／編輯）一句；版面分區（各區有什麼、哪些可點）；進入後之預設狀態；無主選單入口之機制型系統寫明「無獨立畫面」；獨立子系統寫明進入條件（如僅管理者） | 要 |
| 〈重要流程〉 | `- **E2E-NNN**` 案例，三點結構（§5） | 只在 flow 之驗證／備註 |
| 〈測試資料〉（資料變體多者必備） | 具名對象依變體列表：編號／名稱／版次／型別／取用方式／選它的理由；登入帳號引用共用文件之帳號矩陣；統計類頁面之種子資料來源 | 要 |
| 〈畫面元素對照〉 | 區域／元素／提示文字或顯示文字／圖示／定義位置／**出現條件**（狀態 × 權限兩層）／觸發後行為（含中間狀態） | 要 |
| 〈訊息對照〉（編輯類必備；瀏覽類有訊息者亦列） | 觸發情境／訊息文字原文／**樣式**（右上提示、確認對話框、內容區文字、儲存格警示）／**時機**（在什麼事件後多久出現、停留多久）／定義位置；UI 不可達者標明條件 | 要 |
| 〈信件對照〉（寄信類流程必備） | 每種信一列：觸發情境／主旨原文／內文（置換後之逐行純文字，隨機值寫「接亂數新密碼」「接驗證連結」）／定義位置（設定鍵與模板檔）／案例；段首一句交代寄件者之顯示名與位址來源、模板版式、置換值之跳脫規則、e2e 純文字正規化之出處（共用文件）。結果頁（驗證成功／已驗證／無效）之文字列於〈訊息對照〉並各設一張圖。手冊只引主旨不抄內文 | 要 |
| 〈執行前置〉（編輯類） | 資料庫重置與副作用清理之對照（引用共用文件，不重抄） | — |
| 〈規則摘要〉 | 粒度、邊界、順序、契約：實作者最容易假設錯的條件（按鈕出現條件分兩層、內部捲動容器、主選單捲動、訊息時序、暫時狀態圖不比對、資料主從與同步週期、元件之可觀察性、測試環境呈現）；**標準圖之通則**寫一次 | 要 |
| 〈已知落差〉 | 撰寫或實作時發現、由程式碼或實機證成之不一致；spec 自身原載不成立之句；每條帶分類、層級與歸屬（§9） | 要 |

〈觸發〉允許一句話交代本文件範圍與姊妹文件；除此之外**不寫**與其他流程之差異對照、不引用其他流程文件、不展開屬於其他流程之後續行為。UI 上看得到但屬他流程之元件，只寫本流程內可觀察的事實。

## 4. 案例推導：由系統列舉，不由需求文字

1. **可操作元素全清單**：把版面每個按鈕、圖示鈕、標籤、清單列、抽屜把手、鍵盤觸發（快捷鍵、`/` 指令、Enter 送出）、拖曳（寬度、排序）、網址參數列成表；每個元素至少落入一個案例或明寫不設案例之理由（不可達、不可自動化、屬他流程、純裝飾）。
2. **資料變體**：同一功能有幾種資料型別（schema／解析器）、內容型別（附件分組）、版次數（單版／多版）、命中數（零／多），各至少一個案例；具名對象選結果最豐富者，並列於〈測試資料〉。
3. **入口變體**：滑鼠與鍵盤、清單與樹狀、抽屜與彈窗、選單與網址參數，同一動作的每種入口各一案例或明寫共用。
4. **六步真實路徑**：每案例先展開「①起點 → ②進入 → ③前置狀態 → ④輸入 → ⑤反應 → ⑥副作用與離場」，再寫 flow；步數少於真實操作的案例是缺口。
5. **對稱與負向**：新增↔刪除、確定↔取消、就地覆蓋↔升版另存、勾選↔取消勾選、有權限↔無權限、攔截（必填未填、未變更即儲存、未儲存即關閉）、參數合法↔不合法（缺值、值不存在、格式不符各一輪；結果畫面相同亦各列一張圖）；對稱關係只寫在 flow 備註，用於盤查漏格。
6. **姊妹系統對稱**：同一元件、同一種操作在姊妹流程與姊妹系統之案例序列、圖數與判準一致；不可只改其一。
7. **獨立情境為預設，承接式 journey 為例外**：每案例自述完整前置（可在同檔以「先完成○○之操作後」重述），不寫「承 E2E-001 之狀態」；確需連續狀態者於備註標明並讓實作者能以前置步驟重建。
8. **可達性先查**：按鈕外層條件渲染、權限、狀態條件；防禦性提示（未選檔即上傳、無報告即下載、編輯模式無變更時送出鈕不渲染）**不設案例**，於〈訊息對照〉標「UI 不可達」附條件。按鈕出現條件常分兩層（先狀態、再權限），權限負向案例先把狀態推到有權限者確實看得到按鈕。
9. **標籤／chip 類先查可點性**（點擊處理、游標樣式）：同型元素跨系統可點性常不一致，不可概括。
10. **可自動化性與可觀察性先查**：需要作業系統層對話框之取消、需要第二筆才失敗之部分成功、需要拒絕剪貼簿而產品另走可用路徑者，實測造不出即廢止保留編號，理由寫「不可自動化」；其產品觀察仍留〈已知落差〉為靜態事實。作業系統繪製之下拉清單不在 DOM 內：展開可拍、選項只能鍵盤改選，據實寫步驟；元件改為 DOM 浮層後改為兩步四張。可用傳輸層攔截造出之失敗提示（整個主機之請求中止）可設案例，description 只寫使用者看到的事，攔截手段寫在 flow 備註。
11. **權限與主從案例依軸推導**（§6）：畫面軸（入口與按鈕是否出現）、資料軸（資料是否下傳）、進入軸（子系統可否進入）各自列案例，不用一個案例同時主張兩軸；案例不得在次系統修改主系統擁有之資料。
12. 編號一經給定即固定：後續新增只往後加；廢止改成單行「（已廢止，編號保留不再使用；理由：…）」，不順移。

## 5. 案例三點結構（格式與範例見 `references/case-format.md`）

### 5.1 title：使用者觀察視角的一句話，受四個下游限制

- ≤ 25 字，動詞落在使用者視角（顯示、開啟、切換、另開分頁），不寫機制。
- 具名範例以「（以○○為例）」附於尾；**括號內容受手冊 lint 之長度上限**（常見 12 字），超過即縮寫具名對象。
- **全冊唯一**：瀏覽與編輯 spec 會合成同一本手冊，兩份之 title 不得重複（手冊表名以 title 為鍵）。
- 不含禁詞與簡稱（依專案裁決表）；含專案簡稱規則命中之詞者改寫。
- title 改動時，e2e 測試檔之 `it()` 標題與手冊內容檔同步改，改後語法檢查。

### 5.2 description：操作手冊敘述，受眾是使用者

- 骨架「在哪裡 → 做什麼 → 看到什麼 → 什麼時候用得上」；主語是使用者或系統；畫面文字逐字照抄；用途以「便於…」「適合…」收尾。
- **讀完須能答六問**：入口與權限、必要前置、不可逆效果、是否已寫入、成功識別（訊息原文）、失敗如何處理；另附送出方式與可照抄之範例值。入口在可視範圍外者寫「需先於主選單向下捲動才點得到」。
- **不得出現**（以句型與受眾判準，不採詞彙黑名單）：以測試為主語之句型、對測試撰寫者之指示、`檔案:函式`／元件名／變數名、案例編號交叉引用、截圖階段、可改寫成正文之括號夾註、Markdown 強調、需求對應語、含測試字樣之範例值（「本次輸入之說明文字」代替）、待實測標記。
- **會直接進手冊表格，故亦不得含**：`{佔位}`、「→」等符號、禁詞、超長括號；含變數者以描述句表達（「內文為「確認是否刪除」接該項目之名稱」）。
- **位置詞、數量詞、圖示與顏色須與最終畫面一致**（左上／右上、幾個、幾列、捲到哪、圖示形狀）：產圖後對帳（§8 第 3 條）。
- 設計事實對使用者有影響者（勾回之欄位排到最右、儲存後會被週期同步覆寫）以使用者角度提醒，不解釋成因。
- **產品字串含專案內文規則禁用之標點**（主旨前綴「【系統名】」、標題類括號）：description 不逐字抄，改描述句「主旨為「…」並冠以系統名「…」」；spec 之語意項與〈信件對照〉仍寫完整原文（不進手冊）。
- 用詞統一：恢復／點選（清單樹狀）／點擊（按鈕）／「從主選單點選「○○」後」。使用者跨專案裁定之用字（專案 lint 另有規定者從其規定）：計數用阿拉伯數字＋半形空白＋量詞（2 個、4 項；慣用語、序數與圖名除外）；按鍵寫「Enter 鍵」並置「」；須照打之帳號等字串置「」（「Lin_Zhiming」，畫面訊息內照原文）；token 一律「令牌」；「卡片」一律稱「區塊」（英文 panel）；【】〔〕『』《》限標題類，不入 description。

### 5.3 flow：契約等級的測試藍圖（固定 bullet：測試資料、操作、驗證、雙語、清理、備註）

- 判別句：「產品碼改一百行、helper 全部改名，這條還是同一個契約嗎？」是→留；否→丟（helper 名、框架 API、固定等待毫秒、selector 字面都丟）。
- **測試資料**：seed 來源、具名對象（編號、顯示文字、版次）、登入身分與權限（引用帳號矩陣）；fixture 未建者明標。
- **操作**：起點頁 → 使用者動作以「→」串接；按鈕名照畫面原文；每案自述完整前置；入口在可視範圍外者第一步寫「於主選單以滾輪向下捲至○○可見」；有中間狀態之元件寫「點○○下拉展開清單 → 點清單中之『△△』」。
- **驗證**：「語意」列可觀察之文字／URL／存在性（含實測數字，並標明隨種子變動者；已渲染列數是版面產物，不能當資料筆數）；「視覺」以**操作序列**列圖鍵：每步兩張——點擊前框住要點（`<序>-click-xxx`／`type-xxx`／`check-xxx`）→ 點擊後框住**有反應的元素**（具體到「整顆標籤含圖示」「整個彈窗面板含標頭」「當時完整可見之全部節點列」「展開之清單浮層整個」，不寫「框住區域」）；一圖一框；被彈窗蓋住寫「框住彈窗，原目標不框」；短暫訊息寫「框住訊息整顆」且其後之圖註明「訊息淡出後」；暫時狀態（上傳中、處理中、鎖定中）之圖標「暫時狀態，不列入比對」；收合／隱藏／關閉側欄、抽屜、目錄或面板之後的結果圖框因此擴滿或露出之內容區（含標題）或繪圖區，不框新出現之顯示鈕（否則與下一張點擊前之圖相同）；上一步之反應元素確為下一步之目標（如工具列收合後僅餘之設定鈕）時兩張會相同，照列不合併；走到產品缺陷之步驟寫「此圖不產製，偵測到徵狀即標 pending，修復後補產」；下載類至少點擊前一張並寫明無畫面終態；同流程首案例寫一次通則與檔名前綴。
- **清理**：依副作用類型寫具體處置（資料列／實體檔／暫存夾／下載檔／原始碼產生檔／**後端於既定資料夾以外寫出之檔案**／次系統之週期覆寫）並寫回驗方式，不得只寫「由資料庫重置回復」。
- **備註**：實作者才需要的資訊——不可達或不可自動化之證據、`檔案:函式`、與他案及姊妹系統之對稱、共用標準圖之註記、測試手段（傳輸攔截範圍）、量測與操作方式（可點層為帶焦點屬性之容器、提示文字只在停留時渲染不可作定位、內部捲動容器須先捲入）、就緒訊號採使用者可觀察之幾何而非元件內部狀態、測試環境呈現（會出現在標準圖但正式環境沒有之現象）、待實測回填之標記（結案前歸零）。可指向專案規則帳本之條目，不重抄判準。

## 6. 權限與資料主從案例（細節見 `references/permission-and-accounts.md`）

- **先盤點權限模型再寫案例**：至少分「畫面軸」（選單項、入口、按鈕是否出現）、「資料軸」（伺服器回傳前依資料表類別過濾）、「進入軸」（獨立子系統對登入身分之硬性條件）；資料軸常依表類別有多種規則（逐列依等級、隨母表繼承、借用畫面軸之鍵、對已登入者開放）。
- **各軸互不推導**：無某系統之畫面權限，只代表看不到入口，不代表對任何資料表無讀取權；反之亦然。描述觀察時寫「畫面軸擋下」「資料軸依○○表類別規則開放」「進入軸拒絕」，不寫「資料層未擋」「擋法不一致」這類混談句；把設計事實當漏洞呈報會被退。
- **資料主從分明**：多系統共享同一份資料時，共用文件列主從表；次系統之週期覆寫是設計事實；次系統畫面可編修主資料不是缺陷，是「套件有無設定可停用」之問題；「限制不夠嚴」不是缺陷，只有主從方向錯了才是。
- **每個權限案例標明軸別與帳號**；負向案例先滿足狀態條件（§4 第 8 條）。
- **帳號矩陣在共用文件**：所需組合（有畫面權但無操作權、有入口權但無資料權…）種子沒有時，案例廢止保留編號、理由寫「現行種子無此權限組合之帳號，待增設後恢復」，並在共用文件登記待增設清單；不得用管理者帳號假裝。帳號之時間性欄位與測試假時鐘之互動屬環境前置，不是缺陷。
- **入口繞過類**（網址參數、深連結直開）：探測時同時記畫面軸與資料軸之觀察；產品修復後，案例意圖不變則同號改寫為新行為（訊息原文、落回哪裡、查詢是否一併不套用），舊觀察留〈已知落差〉附修復紀錄。

## 7. 事實與數字

- 語意驗證之數字（筆數、節點數、欄位數、視窗寬度門檻、元件矩形）一律**實測後填入**並保留探測 log；隨種子變動者標明，手冊端不會寫它們。
- 具名對象之顯示文字要含唯一化比對字串（同名前綴會混淆者寫完整列文字）。
- 訊息之時機寫實測值（「於資料同步完成後約 0.6 秒顯示，停留約 4 秒」）並附定義處；產品端調整時機後同步改。
- 日期類欄位（上傳時間、變更時間）每次重建都漂移：由測試環境固定時鐘處理，spec 只寫「顯示上傳時間」不寫值，不寫「須遮罩」。
- 畫布類（地圖、三維場景）之像素非決定性：spec 不寫「須遮罩」「填黑」，改寫共用文件所定之覆蓋比對策略，並於視覺項照常列圖鍵。
- **證據落點固定在專案內**（慣例 `spec/evidence/`），不得留在代理之暫存區；引用格式固定：檔名＋段落代號，多輪以檔名區分不覆蓋。
- **「唯一」「已無」「每頁皆」之主張**附可重跑之 grep（對原始碼與產物各一次）與命中數。
- **產物**：前端由套件 `dist` 供應者，spec 描述之行為以產物為準；只改 `src` 未重建產物不算現況。

## 8. 與實作、標準圖、手冊之往返：spec 錯了就改 spec，不改測試遷就

1. 實作者實測發現 spec 與現況不符（遮罩不需要、網址會改寫、階層值不可用、按鈕不存在、位置左右相反、查無資料時彈窗仍開、圖示顏色不同、終態不同）：**直接修正 spec 該句**，並於〈已知落差〉記一條「本 spec 原載『…』不成立：實測…（見 E2E-NNN）」留痕。
2. 標準圖產製時改寫視覺段為逐張列圖鍵並括號寫框住哪個元素；圖鍵、測試檔 `cases` 陣列、寫檔名、比對名四處一致。審圖退回而改框法時同步改括號內文字。
3. **產圖後對帳（交手冊前必做）**：每個案例之 description 與視覺項逐張對圖核對位置詞、數量詞、圖示與顏色、順序描述、圖上有而 spec 未載之標記、被截斷之標題、description 內之測試字樣、終態；不符者改 spec，不留給手冊撰寫者遷就。對帳表為交付物（reference §3）。
4. 產品缺陷：先以無測試 hook 之環境重現確認非測試造成，再依 §9 判定樹分類並寫入〈已知落差〉（症狀、`檔案:函式`、日期、證據、層級），該步依 pending 協定處理；修復後改為「已修復」附修復紀錄，不刪條目。
5. **套件升版或產品修復落在 spec 階段**：先做三件事——全量 diff 原始碼（不只看被建議修復的項目）、確認產物已含、每項以全新頁面實測——才判定「已修復」或「不受影響」；再判案例意圖是否仍在，同號改寫或廢止保留編號；元件可觀察性改變時步驟數隨之改變、姊妹系統同步；只重產受影響之圖；共用文件與姊妹 spec 之同一條目同步（reference §4）。
6. 被判為測試手段造成之現象（截圖方式觸發重排、假時鐘與真時鐘混用之額外資料點、輪詢造成過場卡住、元件內部狀態標記偶發不轉終態）不是產品缺陷，不進〈已知落差〉，記於測試端之偏離紀錄；會出現在標準圖者於 spec 備註載明「測試環境呈現，正式環境無」；就緒訊號改採使用者可觀察之幾何。

## 9. 已知落差：先分層、先查裁決，再分類（判定樹與典型誤判見 `references/gap-classification.md`）

**判定順序（每條候選都走完）**：①定出行為屬於哪一層（共用元件庫／功能套件／部署專案／產品程式碼），找到該層之原始碼、定義、示範頁或設定 → ②查共用文件之裁決紀錄，已裁示者不再提 → ③排除測試手段造成者 → ④是否為刻意設計（元件定義行為、互動一致性之取捨、安全設計、為未來功能預留之寬鬆、元件選型、資料主從）→ ⑤契約缺陷三判準（同型不對稱須兩邊實機比對、承諾未兌現、同一語意兩處行為不同）→ ⑥依層決定處置：本專案可改列缺陷（待修）；上游套件或元件庫列缺陷並依專案約定轉交，不列待裁示；通用套件之功能於本部署不合宜者先查有無設定可停用，無則為擴充需求轉交 → ⑦只剩業主不決定就無法往下做者才待裁示。

- 每條須有證據：`檔案:函式` 或探測 log／截圖；標日期；寫使用者可觀察之後果（「頁內搜尋找不到」「刪除後須重新載入才消失」）；標層級與歸屬。
- 只收三類事實：同型元件互動不對稱、承諾未兌現（有提示無行為、程式意圖與實測相反）、同一語意兩處行為不同；以及 spec 自身原載不成立之句。不收：與舊版文件之差異、業界最佳實踐、推測性風險、「可以更嚴／更好／更一致」之鍍金、拿自製元件規範反推共用元件之對齊問題、姊妹套件程式碼有差異但實機行為相同者。
- **每條帶分類標籤**，四選一：**缺陷（待修）**／**設計事實（記錄備查）**／**待裁示（業主決定）**／**已修復（附修復紀錄）**。「待裁示」只放「業主不決定就無法往下做、且既有原則無法自行決定」之事；設計事實附 `檔案:函式` 即定案，不列待裁示；套件可修者、須等套件更新後才能確認者、開發方向類之提議，皆不是待裁示。
- 權限相關條目必標軸別；跨系統資料相關條目必標主從。
- 修復後標「（已於 YYYY-MM-DD 修復）」並附修復紀錄（版本、改動點、產物證據、實機證據、受影響案例與圖之處置、轉交來源）；不刪。跨流程之同一事實在各 spec 各留一條並互相指向共用文件之彙整條目。
- **產品因業主裁定而改版**（信件模板、文案、註冊開關）而非缺陷者：記為「事實更正（業主裁定 YYYY-MM-DD）」歸設計事實，寫裁定內容、改在哪一層與檔案、受影響案例之同號改寫、對照表之改寫、只重產之圖鍵；spec 原載「不設案例」「本部署未開放」之句一併標原載不成立。
- **口頭裁示當日登記**於共用文件之裁決紀錄；被責備「這之前說過」即代表漏登或漏查。

## 10. 派工模式（多系統、多流程時；細節見 `references/lifecycle-rewrite-reconcile.md` §6）

- 主代理先**探測**（實機事實、可自動化性、帳號矩陣、資料主從、可點層、訊息時機、元件可觀察性）並寫**計畫檔**：每流程一張決定表（案例 × 圖 × 框住什麼 × 語意斷言）與改寫決定（廢止／新增／更正事實）、裁決紀錄之摘錄；決定表填滿才派。
- 每流程一個子代理（新 context）寫 spec 與測試碼；共用守則放一份檔案供所有子代理讀，守則必含：不得由程式碼 diff 判定已修復、評斷共用元件前先讀其原始碼、證據落專案內目錄、待實測標記只放備註與已知落差；標準圖產製由主代理序列排程。
- 子代理回報固定四項：案例對照表（含廢止與理由）、spec 事實更正清單（原載→實測）、已知落差新增條目（含分類與層級）、待主代理裁定事項（每條附「為何既有原則判不了」）。主代理逐條開圖、讀元件原始碼或探測核實後才採納；子代理列的待裁示先自行走判定樹過濾，再決定是否進使用者之回報。

## 11. 回報：做完一次回報，四類分開

- 持續作業期間不分段回報中間結論（使用者無法追蹤零碎訊息）；派工等待期間結束回合只留一句「進行中」。
- 全部做完後一次回報，固定四類：①已完成事項清單；②歸屬上游套件或元件庫之**缺陷**（依專案約定轉交：建議檔或 issue，附證據與建議修法）；③上游套件之**擴充需求**（本部署需要而套件只有整頁開關、缺設定等）；④**真正待裁示**（可能為空，則明說「無待裁示事項」）。
- 待裁示每條先過三問：業主不決定我就無法往下做嗎？之前是否已裁示（查裁決紀錄與代理記憶）？若涉權限或資料，是哪一軸、誰是主？三問任一不過就移出。「這點要裁示什麼」是被退的訊號。
- 不把自己的解讀差異、自創之規則、或「若不是 bug 就沒問題」之觀察列入待裁示。

## 12. 自審與複審

1. 機械掃描 description：`本案例|驗證|截圖|stage[0-9]|E2E-\d|src/|\*\*|（[^）]{12,}）|\{[^}]*\}|→|待實測|待確認`，零命中；有專案 lint 者一併跑。
2. 六問逐條檢核每個 description；title 四限制逐條檢核。
3. 案例對 §4 之清單：每個可操作元素、每種資料變體、每對對稱關係、每個權限軸、每個姊妹系統同型操作都有落點或理由。
4. 產圖後對帳（§8 第 3 條）完成且對帳表零未決；待實測回填標記歸零。
5. 〈已知落差〉每條重走 §9 判定順序，確認層級、分類、證據落點；已裁示者未重列。
6. 外部複審（另一模型或同事）之對象是**表的完整性**（缺軸、缺格、格內事實不屬實附證據），其次才是文句；收回逐條核對源碼再採納。
7. 使用者逐字裁定之句子登記為定稿句，改動須明示；跨流程裁定入共用文件之裁決紀錄與變更紀錄。

## 13. 陷阱與對策（皆已實際踩過）

| 陷阱 | 對策 |
|---|---|
| 沒讀共用元件原始碼就把「選項文字比觸發文字偏移 N 像素」列缺陷 | 元件之錨定定義即如此，另一用法以位移參數對齊亦合法；讀 source、prop 預設、示範頁後才判 |
| 「姊妹套件改了程式碼、本套件沒改」列不對稱缺陷 | 兩邊實機比對；行為相同即非缺陷，再問元件為何如此設計（拖曳換序） |
| 「非管理者仍能進入受限版面」列擴充建議 | 業主已說明為未來功能預留；「可以更嚴」不是缺陷；先查裁決紀錄 |
| 「某頁用原生下拉」列缺陷／建議 | 元件選型由套件決定；spec 只記可觀察後果，套件改元件時步驟隨之改 |
| 「次系統可編修主系統資料」列套件缺陷 | 套件通用；先查有無設定可停用，無則為擴充需求 |
| 以程式碼 diff 判定「已修復」寫進 spec | 全新頁面實測；曾被兩個方向推翻 |
| 升版只改被建議修復之項目 | 全量 diff 原始碼與產物；一處內距改動曾使數十張圖失效 |
| 全部 description 寫成測試理由書，整批被退 | 受眾是使用者；六問＋句型判準，不用詞彙黑名單 |
| description 含 `{名稱}` 佔位進手冊被當引用 | 改描述句 |
| title 括號註記過長、瀏覽編輯同名 | 縮短具名對象；全冊唯一；同步測試檔與手冊 |
| 案例互寫「承 E2E-001」 | 每案自述前置；備註記對稱 |
| spec 寫「須遮罩」「填黑」「網址參數為 X」等未實測之推測 | 實測後改寫並記「原載不成立」 |
| 舊草稿之句子與〈已知落差〉被當事實繼承 | 草稿逐句標已實測／未實測／實作猜測，未實測者重探測 |
| 用單一最簡單之具名對象；內建測試範例對現行種子零命中 | 依變體列舉並選最豐富者；零命中記已知落差，流程改用會命中之輸入 |
| 防禦性提示設了案例卻按不到 | 先查條件渲染；標「UI 不可達」 |
| 取消選檔、拒絕剪貼簿等造不出的情境設了案例 | 可自動化性先查；廢止保留編號，觀察留為靜態事實 |
| 「無畫面權限卻讀得到資料」被寫成漏洞或「擋法不一致」 | 先盤點權限模型，分軸描述；資料軸依表類別之規則是設計事實 |
| 權限負向案例找不到帳號就用管理者硬跑 | 帳號矩陣先查；無組合即廢止並登記待增設 |
| 產品修復後 spec 仍寫舊行為，或刪掉舊觀察 | 同號改寫為新行為，舊觀察留已知落差附修復紀錄 |
| 元件由不可觀察改為可觀察後仍只有一張點擊前之圖 | 拆兩步四張，序號後移，姊妹系統同步 |
| description 之左上／右上、幾個、圖示顏色與圖不符，由手冊撰寫者發現 | 產圖後對帳為交付前必做步驟 |
| 訊息圖拍到空白、或拍到版面尚未載入之過場 | 〈訊息對照〉寫樣式與時機；視覺項註明「訊息整顆」與「淡出後」 |
| 標籤可點性跨系統概括 | 逐系統查點擊處理與游標 |
| 廢止案例順移編號 | 保留編號，單行註記 |
| 已知落差引舊文件或推測；設計事實被列待裁示；已裁示者重提 | 只收程式碼或實機證成者；走判定樹；先查裁決紀錄並當日登記口頭裁示 |
| spec 引用之探測 log 留在暫存區，清理後引用失效 | 證據落專案內固定目錄 |
| 分段回報、把套件可修之事與自創規則丟給使用者裁示 | 一次回報、四類分開、待裁示三問 |
| 視覺項寫「框住區域／右欄」 | 寫到元素：整顆、整個面板含標頭、可見之全部節點列 |
| 寄信類流程無〈信件對照〉，測試與手冊各自猜內文；只做了最先想到的那種信 | 先盤點全部寄信點，每點至少一案例；補〈信件對照〉（逐行純文字）；模板檔、〈信件對照〉、測試期望三處同步並 grep 舊主旨 |
| description 逐字抄含【】之主旨，進手冊被 lint 擋 | 描述句「主旨為「…」並冠以系統名「…」」；原文留語意項與〈信件對照〉 |
| spec 與圖不符卻各自留著 | 以圖為準改 spec 或重產圖，二擇一 |
| 清理只寫「資料庫重置」，後端另在他處寫出檔案或次系統週期覆寫 | 副作用類型含後端寫出之檔案與週期同步，清理寫回驗 |
