# 已知落差之判定樹、缺陷歸屬分層、典型誤判與修復紀錄

本檔為 SKILL.md §9、§11 之落地作法。**先分層讀原始碼，再查裁決紀錄，再套契約判準，最後才分類**；跳過前三步直接分類，是本技能歷來被退最多次的原因。

## 1. 判定樹（每條候選落差逐步走，答案寫進條目）

```
候選現象（實機觀察到、或讀碼推得）
 │
 ├─ 第 0 步 這是「誰」的行為？定出層級（§2），找到該層之原始碼／定義／範例／設定
 │     └─ 找不到原始碼就不得下「缺陷」結論；共用元件庫之行為以其 source、prop 預設值、示範頁為準
 │
 ├─ 第 1 步 已有裁決？查共用文件之裁決紀錄（含口頭裁示已登記者）
 │     └─ 有 → 依裁決寫「設計事實」或「已裁示不處理」，不再提、不列待裁示
 │
 ├─ 第 2 步 是測試手段造成？（截圖方式觸發重排、假時鐘與真時鐘混用、輪詢卡住過場、程式捲動）
 │     └─ 是 → 不進〈已知落差〉；記於測試端之偏離紀錄；若會出現在標準圖，於 spec〈規則摘要〉或備註載明「測試環境呈現，正式環境無」
 │
 ├─ 第 3 步 是刻意設計？（§3 之六種形態）先問「為何如此設計、支援什麼情境」，答得出且有原始碼／文件／裁示支撐 → 設計事實（記錄備查）
 │
 ├─ 第 4 步 契約缺陷判準（三選一，皆須實機證成）
 │     ├─ 同型元素不對稱：**兩邊皆實機比對**，行為真的不同才算；「姊妹套件改了程式碼、本套件沒改」但實機行為相同 → 不是
 │     ├─ 承諾未兌現：有 affordance（游標、箭頭、提示、按鈕）卻無對應行為；程式意圖（如條件渲染）與實測相反
 │     └─ 同一語意兩處行為不同：同一動作在兩個站點結果不同
 │     └─ 三者皆否 → 不是缺陷；若只是「可以更嚴／更好／更一致」→ 鍍金，不寫
 │
 ├─ 第 5 步 落在哪一層（§2）→ 決定處置
 │     ├─ 本專案（部署設定／專案程式碼）可改 → 缺陷（待修）
 │     ├─ 上游套件或共用元件庫 → 缺陷（待修）＋依專案約定轉交（建議檔／issue），**不列待裁示**
 │     └─ 通用套件之功能於本部署不合宜 → 不是缺陷；先查套件有無既有設定可停用，無則為「擴充需求」轉交
 │
 └─ 第 6 步 只剩「業主不決定就無法往下做、且既有原則判不了」者 → 待裁示（業主決定）；三問皆過才放（SKILL §11）
```

## 2. 缺陷歸屬分層（先定層，再談缺陷）

| 層 | 原始碼／定義在哪 | 誰能改 | 這一層「不是缺陷」的常見樣態 |
|---|---|---|---|
| 共用元件庫（下拉、彈出層、表格、日期選擇器…） | 套件內 `src/`、prop 預設值、示範頁、註解 | 元件庫主責者 | 錨定方式、位移參數、動畫、重新顯示欄位之落點——這些是**定義行為**，不同呼叫端用不同參數皆合法 |
| 功能套件（登入、權限、API 管理等可獨立部署之套件） | 套件 `src/`＋`server/`＋語彙檔＋設定項 | 套件主責者 | 套件是**通用**的，功能比本部署需要的多不是缺陷；問題是「有無設定可停用」 |
| 部署專案（設定檔、接線、種子、部署層之授權判斷） | 專案根之設定與 `server/` 接線 | 本專案 | 授權強度、資料主從之接線、同步週期——多為業主裁示之設計事實 |
| 產品程式碼（本專案自有頁面與元件） | 專案 `src/` | 本專案 | — |

規則：**同一現象在不同層有不同結論**。例：元件支援中文化而套件未傳設定 → 缺陷在功能套件層；元件之唯讀態仍給手指游標 → 缺陷在元件庫層；次系統畫面可編修主系統擁有之資料 → 功能套件層屬通用功能，本部署層要的是「設定可停用」→ 擴充需求。

## 3. 刻意設計之六種形態（第 3 步的自問清單）

| 形態 | 判別問句 | 典型例（去識別） |
|---|---|---|
| 元件定義行為 | 元件原始碼／prop 預設值／示範頁是否就是這樣寫？ | 彈出清單錨定「觸發文字」而非「圓角外框」；另一呼叫端以位移參數把清單拉回外框——兩種用法皆合法 |
| 互動一致性之取捨 | 這個行為是否為了另一個互動（拖曳換序、多選、還原）而必須如此？ | 隱藏欄位再顯示一律置於最右——因欄位支援拖曳換序，原位置已不可信 |
| 安全設計 | 是否為防列舉、防猜測、防重放？ | 帳號不存在／密碼錯／已鎖定顯示同一訊息 |
| 為未來功能預留之寬鬆 | 業主是否說過要支援日後給某類使用者之功能？ | 非管理者仍可進入受限之後台版面 |
| 元件選型 | 用原生元件還是自製元件，是不是套件自己的決定？ | 某頁仍用原生下拉——套件決定；e2e 與 spec 跟隨，只記錄「清單不在 DOM，展開步驟拍不到」之可觀察後果 |
| 資料主從與同步 | 這個系統對這份資料是主還是次？次系統之覆寫、週期同步是否為設計？ | 權限系統每 N 秒以登入系統之使用者覆寫本地——設計事實；「次系統畫面可改主系統資料」是設定／擴充問題 |

**判別不了時的動作**：讀該層原始碼與註解 → 讀示範頁／文件 → 實機比對兩個站點 → 仍不確定才在回報中以「疑似」呈現並附證據，不寫成缺陷。

## 4. 典型誤判（皆已實際發生；每列＝一種錯誤形狀）

| 誤判 | 錯在哪一步 | 正解 |
|---|---|---|
| 「選項文字比觸發文字右偏 N 像素」列缺陷 | 第 0 步：沒讀元件原始碼，拿專案之自製選單規範反推共用元件 | 元件錨定定義即如此；全域／專案 UI 規範管的是自製元件，不能反推共用元件為錯 |
| 「姊妹套件已加排序、本套件沒加」列缺陷 | 第 4 步：不對稱只從程式碼差異推得，未實機比對 | 兩邊實機行為相同；且該行為是表格元件為拖曳換序之刻意設計 |
| 「非管理者仍可進後台版面」列擴充建議 | 第 1、3 步：業主已說明為未來功能預留 | 設計事實；「可以更嚴」不是缺陷 |
| 「某頁用原生下拉、應改自製」列缺陷／建議 | 第 3 步：元件選型是套件的決定 | 記錄可觀察後果即可；套件改元件時 spec 跟著改步驟 |
| 「次系統畫面可編修主系統資料」列套件缺陷 | 第 5 步：套件是通用的 | 先查套件有無設定可停用；無 → 擴充需求轉交，非缺陷、非待裁示 |
| 「多種失敗同一訊息」列待裁示 | 第 3 步：安全設計 | 設計事實，e2e 照實截圖 |
| 「無某系統畫面權限卻讀得到某表」列漏洞 | 分軸（permission-and-accounts.md） | 畫面軸擋下、資料軸依表類別開放，兩句分開寫 |
| 「元件可中文化但畫面是英文」列待裁示 | 第 5 步 | 套件未傳設定 → 套件層缺陷，轉交 |
| 以 diff 讀碼判定「已修復」寫進 spec | 事實來源：程式碼推導只是假設 | 每項以全新頁面實測；曾兩度被推翻（碼看似未修實已修、碼看似已修實未修） |
| 只改「被建議修復」的那幾項 | 升版改寫範圍：套件實際改動多於建議項 | 全量 diff 原始碼與產物，逐案例判定影響（lifecycle §4） |
| 「文件 A 與已刪之文件 B 不一致」列待裁示 | 自己的解讀差異當缺口 | 先問語意是否真的衝突；業主口頭一句即可解者不列 |
| 自創規則後把「規則被違反」列待裁示 | 先查全域／專案既有規範 | 沒有依據的規則不得成為缺口 |
| 連續兩張相同之標準圖列缺陷 | 每步兩張之自然結果 | 照列不合併，不列 |
| 紅框畫在同色按鈕上不可辨再列一次 | 第 1 步：已裁示暫不處理 | 不再提 |
| 統計圖末端多一格當日日期列已知落差 | 第 2 步：假時鐘與真時鐘混用之測試手段 | 記測試端偏離；spec 備註載明測試環境呈現 |

## 5. 已修復判定與修復紀錄

**已修復之判定只認實機**：升版或修復後，每一項以**全新頁面**（不沿用同一頁面內之前置操作，避免狀態污染）重現一次；程式碼 diff 只用來定位「該去哪裡看」。判定為已修復者，spec 條目改為「已修復（附修復紀錄）」，**修復紀錄必含**：

1. 修在哪一層、哪個版本（套件名與版號，或部署改動之日期）。
2. 改動點（檔名＋函式或模板區塊；不引行號亦可，行號會漂移）。
3. 產物已含之證據（前端由套件 `dist` 供應者，須 grep 產物確認改動已編入；只改 `src` 未重建 `dist` 則畫面不變）。
4. 實機證據（探測 log 檔名＋段落代號，或標準圖檔名）。
5. 受影響案例與標準圖之處置（同號改寫哪些案例、重產哪些圖、新增／改名／刪除哪些圖鍵）。
6. 若原條目曾以建議檔／issue 轉交，記其來源與已收回。

舊觀察不刪；同一事實在各流程 spec 各留一條並指向共用文件之彙整條目。

## 6. 已知落差條目格式

`- **<一句話標題>（<分類>；發現於 <日期>[，<日期> 修復]）**：<症狀與證據（檔案:函式 或 探測 log 檔名＋段落）>。使用者可觀察之後果：<…>。<層級與歸屬>。<處置／修復紀錄（§5）>。`

分類四選一：缺陷（待修）／設計事實（記錄備查）／待裁示（業主決定）／已修復（附修復紀錄）。權限相關者標軸別；跨系統資料相關者標主從。spec 自身原載不成立者：「本 spec 原載『…』不成立：實測…（見 E2E-NNN）」，分類多為設計事實。

## 7. 證據之落點與引用

- 探測 log、截圖等佐證**必須放在專案內之固定目錄**（慣例 `spec/evidence/`），不得留在 AI 代理之暫存區（會被整批清除，spec 之引用隨之失效）。
- 引用格式：`<檔名>` 之 `<段落代號或行首標記>`；多輪探測以檔名帶日期或輪次區分，不覆蓋舊檔。
- 「全系統唯一」「已無任何 X」「每頁皆」之主張，附可重跑之 grep（對原始碼與產物各一次）與命中數。
