# spec 之生命週期：從零撰寫、改寫舊草稿、產圖後對帳、產品修復後改寫、不可自動化判準、派工模式

本檔為 SKILL.md §2、§4 第 10 條、§8、§10 之流程細節。每節皆有：步驟、產物、失敗對策。

## 1. 從零撰寫（無任何 spec）

**步驟**

1. **系統列舉表**：分頁 × 區塊（目錄節、卡片、表格）× 每區塊之可操作元素（按鈕、勾選、連結、輸入框、拖曳、鍵盤）× 訊息（grep 所有提示呼叫，逐則標「可達／UI 不可達／需失敗注入」）。表上每格都要有落點（案例編號）或理由。
2. **探測**：每條路徑實機走一遍，記畫面文字、矩形、就緒訊號（以使用者可觀察之結果為準，如「結果表格列數＝N」）、訊息樣式與時機、下載檔名格式。
3. **具名輸入選擇**：取自現行種子且結果最豐富者；內建之「測試範例」若對現行種子零命中，仍可設「使用測試範例」案例（畫面行為是事實），但流程主線改用會命中之輸入，零命中記〈已知落差〉（設計事實或待裁示，附範例來源行號與種子差異）。
4. **決定表**：每案例一列：圖鍵序列 × 框住什麼 × 語意斷言；先填表再寫案例，視覺項由表轉寫。
5. 依骨架寫 spec；登記 flow 代號於共用文件。

**產物**：系統列舉表、探測 log、決定表、spec。
**失敗對策**：探測不到的元素（提示文字只在停留時渲染、可點層與可見層不同）記在備註供實作者，不寫進 description。

## 2. 改寫舊格式草稿（草稿早於現行通則）

**步驟**

1. **逐句分類**：草稿每句標三類之一——已實測（附證據）／未實測（「尚未實測」「預期」「應該」等字樣）／實作猜測（「須遮罩」「填黑」「參數為 X」「共用 helper」）。
2. 未實測句一律重探測後改寫；實作猜測句刪除（時間欄位由固定時鐘處理、畫布由共用覆蓋策略處理、網址是否改寫以實測為準）。
3. **〈已知落差〉逐條重驗**：有的已不成立、有的是舊文件比對出來的（刪）、有的需改分類；保留者補證據與日期。
4. **視覺段全部改為操作序列**（每步兩張、括號寫到元素）；舊的「截圖一張整頁」寫法不保留。
5. 需要不存在之帳號或造不出之情境者廢止保留編號（§5）。
6. description 已是手冊體者只補六問缺項、改測試字樣與位置詞，不重寫風格；title 依四限制檢核。
7. 編號一律保留；新增只往後加。

**產物**：逐句分類表（可放暫存區）、更正清單（原載→實測，寫進〈已知落差〉與共用文件變更紀錄）。
**失敗對策**：草稿看起來很完整時最容易整段繼承——分類表沒填完不得動筆改寫。

## 3. 產圖後對帳（交手冊前必做）

標準圖是使用者實際會看到的畫面；description 會逐字進手冊。產完圖（並經審圖）後，逐案例開圖對 description 與視覺項核對下列項目，做成對帳表（案例 × 項目 × 結果 × 處置）：

| 對帳項目 | 常見不符 |
|---|---|
| 位置詞 | 「表格右上」實為左上；「內容區右上」實為左上 |
| 數量詞 | 「十個計畫」實為九個；「兩列」實為一列展開兩子列 |
| 順序／捲動描述 | 「回到最上方」實為「該節標題回到可視範圍上方、頂端警語捲出」 |
| 圖上有而 spec 未載之元素 | 目錄項之高亮、篩選標記、額外欄位、遊標所在區塊之小工具列 |
| 標題截斷 | 畫面截斷者採 spec 之完整名，並註明 |
| description 內之測試字樣 | 範例值含「測試」「e2e」者改中性描述 |
| 訊息圖之畫面狀態 | 訊息出現時版面是否已載入；若否，是產品時機或測試時機問題，回 e2e 端 |
| 連續相同之兩張圖 | 上一步之反應元素恰為下一步之目標時屬規則之自然結果，不是缺陷，照列 |

不符者改 spec（description、視覺項括號、〈畫面元素對照〉補列），並於〈已知落差〉留「原載不成立」；不留給手冊撰寫者遷就，也不在手冊端改寫表格文字。

## 4. 產品修復觸發之改寫

1. **判定案例意圖是否仍在**：意圖不變（同一情境、不同結果）→ 同號改寫；情境本身消失 → 廢止保留編號。
2. 改寫內容：title（如需）、description（新行為之訊息原文、落在哪、如何處理）、flow（操作不變、驗證改新觀察、視覺項改新序列）、〈訊息對照〉新增訊息（樣式、時機、行號）、〈規則摘要〉加契約句。
3. 〈已知落差〉原條目不刪：標「（已於 YYYY-MM-DD 修復）」＋修法摘要＋修復後實測（帳號、情境、結果）；姊妹 spec 之同一事實條目同步標記；共用文件之裁示彙整同步。
4. 只以受影響案例重產標準圖（產前記其餘圖之修改時間，產後回驗未變）；spec 之舊圖鍵不再存在者刪檔。
5. 修復若牽涉訊息時機（提示在版面載入前就發出而使用者看不到），時機屬產品行為，改產品並把實測時機寫進〈訊息對照〉；測試端只調整等待順序。

## 5. 不可自動化與傳輸層攔截之判準

| 情境 | 判準 | spec 寫法 |
|---|---|---|
| 檔案／資料夾選擇之「取消」 | 測試框架對目錄型選擇無法送空清單 | 案例廢止保留編號；產品在取消時之行為（如殘留前次檔案）留〈已知落差〉為靜態事實 |
| 剪貼簿被拒 | 只拒 API 權限時產品若走另一條可用路徑，情境造不出 | 廢止；「未檢查回傳值」之靜態事實保留 |
| 部分成功（第二筆才失敗） | 二進位單一端點無法選擇性攔截 | 廢止；下沉 api 層列後續工項 |
| 讀取／上傳失敗提示 | 對整個後端主機之請求中止可造出 | 可設案例：description 只寫使用者看到的訊息與復原方式；flow 備註寫攔截範圍與掛載時機（就緒後掛、觸發後即解除），並註明對哪個 origin 掛才命中 |
| 需第三方系統之狀態（未登入往返） | 可造出者照設；參數是否保留以實測為準 | 實測結果寫〈已知落差〉（保留或不保留皆為事實） |

## 6. 派工模式（多系統、多流程）

**主代理**

1. 探測：共用普查（選單、帳號矩陣、可視範圍、傳輸方式）＋各系統探測（畫面文字、矩形、訊息、就緒訊號、可自動化性）；產物為探測 log 與截圖。
2. 計畫檔：§0 共通決定（帳號、可自動化性、攔截、暫存與副作用、入口捲動）→ 各系統節：實測事實表（編號、事實、證據）、spec 改寫決定（廢止／新增／更正）、決定表（案例 × 圖 × 框住 × 語意）、程式結構 → 工作規則 → 交付清單。**決定表填滿才派**。
3. 共用守則檔：必讀清單、唯一可改之檔案、暫存位置、回報格式、兩階段規則（階段 A 寫 spec 與測試碼不產圖；階段 B 由主代理逐一放行產圖，同一時間只有一條產製鏈）。
4. 派工提示：只指向計畫檔之該節與守則檔，另列「由子代理補探測」之項目清單；子代理不得改他系統之檔案。
5. 收回：對子代理之「spec 事實更正」逐條開圖或探測核實；對「已知落差」逐條檢查分類與證據；對「待主代理裁定」逐條裁定並回寫計畫檔。

**子代理回報固定四項**：案例對照表（含廢止與理由）／spec 事實更正清單（原載→實測，附證據）／〈已知落差〉新增條目（含分類）／待主代理裁定事項。

**失敗對策**：子代理把計畫檔之事實當成不必再驗 → 提示明令「計畫檔標『由子代理實測』者必補探測，其餘亦以實機為準，衝突時回報不自行改決定表」。
