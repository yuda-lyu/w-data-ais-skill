# spec 之生命週期：從零撰寫、改寫舊草稿、產圖後對帳、升版與修復後改寫、不可自動化判準、派工模式

本檔為 SKILL.md §2、§4 第 10 條、§8、§10 之流程細節。每節皆有：步驟、產物、失敗對策。

## 1. 從零撰寫（無任何 spec）

**步驟**

1. **系統列舉表**：分頁 × 區塊（目錄節、面板、表格）× 每區塊之可操作元素（按鈕、勾選、連結、輸入框、拖曳、鍵盤）× 訊息（grep 所有提示呼叫，逐則標「可達／UI 不可達／需失敗注入」）。表上每格都要有落點（案例編號）或理由。
2. **探測**：每條路徑實機走一遍，記畫面文字、矩形、就緒訊號（以使用者可觀察之結果為準，如「結果表格列數＝N」）、訊息樣式與時機、下載檔名格式；探測 log 落專案內之證據目錄（gap-classification.md §7）。
3. **具名輸入選擇**：取自現行種子且結果最豐富者；內建之「測試範例」若對現行種子零命中，仍可設「使用測試範例」案例（畫面行為是事實），但流程主線改用會命中之輸入，零命中記〈已知落差〉（設計事實或待裁示，附範例來源與種子差異）。
4. **姊妹系統先例**：同組織已有同型元件（統計頁下拉、關聯對話框、抽屜收合）之案例序列者，以先完成者為範本，序列與圖數對齊；差異須有理由並寫在備註。
5. **決定表**：每案例一列：圖鍵序列 × 框住什麼 × 語意斷言；先填表再寫案例，視覺項由表轉寫。
6. 依骨架寫 spec；登記 flow 代號於共用文件。

**產物**：系統列舉表、探測 log、決定表、spec。
**失敗對策**：探測不到的元素（提示文字只在停留時渲染、可點層與可見層不同）記在備註供實作者，不寫進 description。

## 2. 改寫舊格式草稿（草稿早於現行通則）

**步驟**

1. **逐句分類**：草稿每句標三類之一——已實測（附證據）／未實測（「尚未實測」「預期」「應該」等字樣）／實作猜測（「須遮罩」「填黑」「參數為 X」「共用 helper」）。
2. 未實測句一律重探測後改寫；實作猜測句刪除（時間欄位由固定時鐘處理、畫布由共用覆蓋策略處理、網址是否改寫以實測為準）。
3. **〈已知落差〉逐條重驗**：有的已不成立、有的是舊文件比對出來的（刪）、有的需改分類；保留者補證據與日期，並依 gap-classification.md §1 重走判定樹。
4. **視覺段全部改為操作序列**（每步兩張、括號寫到元素）；舊的「截圖一張整頁」寫法不保留。
5. 需要不存在之帳號或造不出之情境者廢止保留編號（§5）。
6. description 已是手冊體者只補六問缺項、改測試字樣與位置詞，不重寫風格；title 依四限制檢核。
7. 編號一律保留；新增只往後加。

**產物**：逐句分類表（可放暫存區）、更正清單（原載→實測，寫進〈已知落差〉與共用文件變更紀錄）。
**失敗對策**：草稿看起來很完整時最容易整段繼承——分類表沒填完不得動筆改寫。

## 3. 產圖後對帳（交手冊前必做）

標準圖是使用者實際會看到的畫面；description 會逐字進手冊。產完圖（並經審圖）後，逐案例開圖對 description 與視覺項核對下列項目，做成對帳表（案例 × 項目 × 結果 × 處置）：

| 對帳項目 | 常見不符 |
|---|---|
| 位置詞 | 「表格右上」實為左上；「內容區右上」實為左上 |
| 數量詞 | 「十個計畫」實為九個；「兩列」實為一列展開兩子列 |
| 順序／捲動描述 | 「回到最上方」實為「該節標題回到可視範圍上方、頂端警語捲出」 |
| 圖上有而 spec 未載之元素 | 目錄項之高亮、篩選標記、額外欄位、遊標所在區塊之小工具列 |
| 圖示與顏色 | spec 寫「紅色禁止圖示」，圖上是藍色鎖頭圖示 |
| 標題截斷 | 畫面截斷者採 spec 之完整名，並註明 |
| 終態 | 「刪除後顯示『尚未選擇』」實為自動改選第一筆 |
| description 內之測試字樣 | 範例值含「測試」「e2e」者改中性描述 |
| 訊息圖之畫面狀態 | 訊息出現時版面是否已載入；若否，是產品時機或測試時機問題，回 e2e 端 |
| 連續相同之兩張圖 | 上一步之反應元素確為下一步之目標（工具列收合後僅餘之設定鈕）時屬規則之自然結果，照列；收合／隱藏／關閉後之圖框到新出現之開啟鈕而與下一張相同者是框錯對象，改框擴滿之內容區並重產 |
| 測試環境呈現 | 假時鐘與真時鐘混用造成之額外資料點——記測試端偏離並於 spec 備註載明「測試環境呈現，正式環境無」 |

不符者改 spec（description、視覺項括號、〈畫面元素對照〉補列），並於〈已知落差〉留「原載不成立」；不留給手冊撰寫者遷就，也不在手冊端改寫表格文字。

## 4. 升版與產品修復觸發之改寫（三件事先做完，才動 spec）

**觸發**：上游套件升版、共用元件庫升版、部署設定改動、產品缺陷修復。

**三件事（缺一即不得宣稱「已修復」或「不受影響」）**：

1. **全量 diff 原始碼**：對升版套件之整個 `src`（與 `server`、語彙檔、設定項）逐檔 diff，不只看「被建議修復」那幾項——實際改動常多於建議項（曾有建議 1 項、實際 4 項會動到畫面；曾有一處內距改動使數十張圖失效）。列出每一項會動到畫面或操作方式者。
2. **確認產物已含**：前端由套件 `dist` 供應者，grep 產物確認改動已編入；只改 `src` 未重建產物則畫面不變，spec 不得先改。
3. **全新頁面實機重驗每一項**：每項各開一個全新頁面走一次；不在同一頁面串接多項（狀態污染會製造假訊號）。程式碼推導只是假設——曾被兩個方向推翻（碼看似未修實已修、碼看似已修實未修）。

**再判定案例意圖**：意圖不變（同一情境、不同結果）→ 同號改寫；情境本身消失 → 廢止保留編號。

**改寫內容**：title（如需）、description（新行為之訊息原文、落在哪、如何處理）、flow（操作不變、驗證改新觀察、視覺項改新序列）、〈訊息對照〉新增訊息（樣式、時機、位置）、〈規則摘要〉加契約句、〈畫面元素對照〉之元素與觸發後行為。

**元件可觀察性改變時**：原本不在 DOM 內、拍不到也點不到的中間狀態（作業系統繪製之下拉清單、原生對話框）被改為 DOM 元件後，該操作由一步變兩步（展開清單 → 點選項），標準圖由一張變四張（點擊前 → 清單展開 → 點選項前 → 結果），其後圖鍵序號後移；反向亦然。姊妹系統之同型操作同步改為同一序列（對稱）。

**〈已知落差〉**：原條目不刪，改「已修復（附修復紀錄）」並依 gap-classification.md §5 填修復紀錄；姊妹 spec 之同一事實條目同步；共用文件之裁決紀錄與變更紀錄同步。

**標準圖**：只以受影響案例重產（產前記其餘圖之修改時間，產後回驗未變）；圖鍵序號後移者以新檔名重產、舊檔名於逐張目視通過後刪除；spec 之舊圖鍵不再存在者刪檔。「受影響」以「該改動在這張圖上看得見嗎」逐張開既有圖判定，不憑案例名推論。

**訊息時機**：修復若牽涉訊息時機（提示在版面載入前就發出而使用者看不到），時機屬產品行為，改產品並把實測時機寫進〈訊息對照〉；測試端只調整等待順序。

**待實測回填之標記**：階段性改寫時尚未實測之句，標記只放在 flow 備註或〈已知落差〉，不放進 description；結案前逐條回填並附證據，歸零後才交付。

## 5. 不可自動化與傳輸層攔截之判準

| 情境 | 判準 | spec 寫法 |
|---|---|---|
| 檔案／資料夾選擇之「取消」 | 測試框架對目錄型選擇無法送空清單 | 案例廢止保留編號；產品在取消時之行為（如殘留前次檔案）留〈已知落差〉為靜態事實 |
| 剪貼簿被拒 | 只拒 API 權限時產品若走另一條可用路徑，情境造不出 | 廢止；「未檢查回傳值」之靜態事實保留 |
| 部分成功（第二筆才失敗） | 二進位單一端點無法選擇性攔截 | 廢止；下沉 api 層列後續工項 |
| 讀取／上傳失敗提示 | 對整個後端主機之請求中止可造出 | 可設案例：description 只寫使用者看到的訊息與復原方式；flow 備註寫攔截範圍與掛載時機（就緒後掛、觸發後即解除），並註明對哪個 origin 掛才命中 |
| 需第三方系統之狀態（未登入往返） | 可造出者照設；參數是否保留以實測為準 | 實測結果寫〈已知落差〉（保留或不保留皆為事實） |
| 作業系統繪製之下拉清單 | 不在 DOM 內：可截圖（瀏覽器自繪）但滑鼠點不到選項，鍵盤可改選 | 展開步驟可拍一張、選項步驟以鍵盤操作；套件改為自製元件後依 §4 改為兩步四張 |

## 6. 派工模式（多系統、多流程）

**主代理**

1. 探測：共用普查（選單、帳號矩陣、可視範圍、傳輸方式、資料主從）＋各系統探測（畫面文字、矩形、訊息、就緒訊號、可自動化性）；產物為探測 log 與截圖。
2. 計畫檔：§0 共通決定（帳號、可自動化性、攔截、暫存與副作用、入口捲動、裁決紀錄之摘錄）→ 各系統節：實測事實表（編號、事實、證據）、spec 改寫決定（廢止／新增／更正）、決定表（案例 × 圖 × 框住 × 語意）、程式結構 → 工作規則 → 交付清單。**決定表填滿才派**。
3. 共用守則檔：必讀清單、唯一可改之檔案、暫存位置、證據落點、回報格式、兩階段規則（階段 A 寫 spec 與測試碼不產圖；階段 B 由主代理逐一放行產圖，同一時間只有一條產製鏈）。
4. 派工提示：只指向計畫檔之該節與守則檔，另列「由子代理補探測」之項目清單；子代理不得改他系統之檔案。
5. 收回：對子代理之「spec 事實更正」逐條開圖或探測核實；對「已知落差」逐條重走判定樹（gap-classification.md §1）並核實層級；對「待主代理裁定」逐條裁定並回寫計畫檔——子代理列的待裁示大多是設計事實或可自行決定者，過濾後才向使用者回報。

**子代理守則（寫進守則檔）**

- 計畫檔標「由子代理實測」者必補探測；其餘亦以實機為準，衝突時回報不自行改決定表。
- **不得由程式碼 diff 判定「已修復」**；每項以全新頁面實測，未實測者標「待實測回填」（只放 flow 備註／已知落差），階段 B 必回填。
- 評斷共用元件之呈現前先讀元件原始碼與定義；不拿全域／專案之自製元件規範反推共用元件。
- 探測 log 落專案內證據目錄；spec 引用之檔案不得在暫存區。
- 回報固定四項：案例對照表（含廢止與理由）／spec 事實更正清單（原載→實測，附證據）／〈已知落差〉新增條目（含分類與層級）／待主代理裁定事項（每條附「為何既有原則判不了」）。

**失敗對策**：子代理把計畫檔之事實當成不必再驗 → 提示明令上述守則；子代理連續回報「待裁示」→ 主代理先自行走判定樹，再決定要不要進使用者之回報。
