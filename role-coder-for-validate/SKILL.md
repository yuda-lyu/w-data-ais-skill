# 程式開發自檢規範：綠燈不等於正確

> **撰寫基準**：本技能以 Claude Opus 5 為預設執行模型撰寫。請照章節順序執行，每一步都要留下指定的產物檔；不要跳步，不要用「我測過了」「看起來會動」取代產物。更強的模型可以合併步驟，但產物與回報格式不可省略。

## 0. 一分鐘看懂：什麼時候用、要交出什麼、什麼叫完成

**什麼時候用**：你寫了（或正在改、正在審）程式——新功能、修 bug、重構、順手改都算。宣告完成之前、任何檢查失敗之後、審別人的程式之前，都要走一遍本技能。

**要交出什麼**（全部放在 `./tmp/`，或使用者指定的專案 docs 目錄）：

| # | 檔案 | 內容 | 對應步驟 |
|---|---|---|---|
| 1 | `validate-plan.md` | 需求述語、約束清單、輸入空間表、對標結果、做哪些層與理由 | Step 0、Step 1 |
| 2 | `validate-matrix.md` | 需求可追溯矩陣：每條需求 → 述語 → 檢查 → 證據 → 判定 | 全程 |
| 3 | `validate-entities.md` | 實體帳冊：用到的每個 API、選項、旗標是否真的存在於已安裝版本 | L0d |
| 4 | `validate-check-log.md` | 每一層檢查的指令、輸出摘要、判定 | L0a–L6 |
| 5 | `validate-rootcause.md` | 每次失敗的歸類、重現測試、根因、同類掃描、修正、重跑範圍 | §7 |
| 6 | `validate-acceptance.md` | 使用者視角驗收紀錄：輸入空間表每一格的實際操作與結果 | L5 |
| 7 | 回覆末尾 | 覆蓋聲明（§8 模板） | 全部 |

**什麼叫完成**（三件同時成立才可以寫「完成」）：

1. 既有測試全綠（回歸），而且新增的測試對應到需求矩陣上的述語。
2. 輸入空間表與需求矩陣沒有空白格；每一格是「已證」「刻意不做（有理由）」「已知不修（有理由）」三者之一。
3. 使用者視角驗收做過：用真瀏覽器或真指令對表上每一格實際操作一遍，發現全部寫進回報（包含需求範圍外的）。

只有第 1 件成立就宣告完成，等於沒完成。

## 1. 名詞定義

| 名詞 | 意思 | 例子 |
|---|---|---|
| 可驗證述語 | 把需求改寫成「給定輸入 X，可觀察到結果 Y」的句子，能被測試或實測斷言 | 需求「派工前先檢查沙箱設定」→ 述語「給定 marker 檔不存在，函式回傳 `ok=false` 且不 spawn 子程序」 |
| 輸入空間表 | 把需求所屬類別的所有輸入組合列成表：先列軸，每軸的成員用 grep 從系統取得，軸與軸做笛卡兒積，每一格填「現況／應然／處置」 | 互動類：可命中元素 × 事件 × 滑鼠鍵 × 進行中手勢 × 終止路徑；資料流類：入口 × 前置狀態 × 並發 × 失敗點 × 清理路徑 |
| 兄弟元素 | 同一類別裡的其他成員；規則套到其中一個，就要逐一檢查其他的 | 節點、邊、把手、畫布、工具列；上市、上櫃；成功路徑、錯誤路徑 |
| 接縫 | 程式與鄰接系統的邊界 | HTTP 端點、資料庫、檔案系統、外部 CLI、第三方 API |
| 現狀指紋測試 | 只斷言「跟上次跑出來一樣」的測試（例如 `buf.equals(baseline)`）；系統偏離 spec 時它也是綠的 | 相對的是「spec 翻譯測試」：每條斷言對應 spec 的一句話 |
| 終止路徑／清理路徑 | 一個動作或流程結束的所有方式，以及結束後要收拾的東西 | mouseup、blur、destroy、旗標切換；DB 殘留、記憶體殘留、暫存檔、子程序 |
| 實體 | 程式中可以用工具查「存不存在」的名字 | import 的符號、套件版本、選項鍵、CLI 旗標、設定鍵、環境變數、API 端點、資料表與欄位 |
| 產物 | 一份別人可以逐格檢查的表或紀錄檔 | §0 列的檔案 |

## 2. 本技能要抓的三種錯

| 模式 | 定義 | 在程式上的症狀 | 靠哪一步抓 |
|---|---|---|---|
| 漏做（the miss） | 該做的沒做；做出來的都對，但不完整 | 修了 A 元素沒修對稱的 B；只做成功路徑沒做錯誤／終止／清理路徑；只做一種語系或平台；有 A→B 沒有 B→A；輸入空間表有空白格 | Step 1 輸入空間表、Step 6 漏做掃描、L5 |
| 捏造（the hallucination） | 用了不存在或不為真的東西 | 呼叫不存在的函式、選項、旗標、設定鍵；假設某版本套件有某 API 卻沒查；註解描述的行為與程式不符；範例程式是想像出來的 | Step 7 實體帳冊（L0d）、L0a |
| 誤解（the misinterpretation） | 需求略含糊，盡力做了仍做錯 | 需求有歧義，自己挑一種解釋沒有說；使用者投訴一句，你只修那一點而不是整個類別；做了使用者沒要的（鍍金）；讀錯既有慣例或場景 | Step 0 述語化、Step 8 使用者視角驗收 |

共同根因之一是 **context rot**：長任務做到後段，會忘記前段的約束（例如「不得改既有 UI」「沿用既有 canonical 寫法」），重複寫已經有的函式，或違反開頭定下的介面。所以：約束清單寫進 `validate-plan.md`，每個檢查點重讀一次；找既有實作用 grep，不靠記憶。

## 3. 三條鐵則

驗證有三個角色：**人**、**AI**、**確定性工具**（編譯器、lint、測試、腳本）。任何一方單獨都做不到規模化，三者要輪流上場。每兩個角色的配對各有一個典型失敗，翻成三條鐵則：

**鐵則一：紅燈或 bug 回報時，先重現，再修根因，不可以直接改到綠。**（人＋AI 的失敗：「你說得對」——人抓到一個錯，AI 只修那一個，不找為什麼會錯。）
做法：先寫一個會失敗的重現測試；把根因讀到 `檔案:行號`；歸類成漏做、捏造或誤解；寫下同類判準；全範圍掃描同類；全部修掉；重跑該層與其下各層。詳見 §7。

**鐵則二：綠燈只證明「被測到的東西」，不證明需求正確。**（AI＋工具的失敗：「我徹底辜負了你」——lint 過、build 過、既有測試綠，但行為不合需求；或測試是現狀指紋，系統偏離 spec 也是綠的。）
做法：新增的測試每一條斷言都要對應到需求矩陣上的一個述語（spec 翻譯），不是「跟上次一樣」；完成之前一定做使用者視角驗收（L5）。回報時不可以用「測試都過」暗示需求已滿足。

**鐵則三：會重複做的手工檢查，要寫成腳本或測試，而且每次改動後全部重跑。**（人＋工具的失敗：「這也要自動化？」——每次改完手動點三下看看，第五次就不點了，回歸從此沒人抓。）
做法：第一次手動驗過的東西，馬上寫成 `./tmp/` 腳本或測試；之後每次改動（包含「只改一行」）都重跑整個階梯，不只重跑紅的那一條。

## 4. 每個檢查先回答六個問題

在執行任何一項檢查之前，先回答：

1. **檢查什麼？**——具體跑什麼、審什麼、量什麼。
2. **建置成本？**——時間、專業、需不需要資料、環境或鄰接系統。
3. **誰執行？**——確定性工具、AI、人，或組合。
4. **實際證明了什麼？**——誠實寫出這項檢查「只」能證明什麼。例如：單元測試綠只證明測到的路徑，不證明整合接縫。
5. **產物是什麼？**——一份具體、可勾選、可以直接據以修改的東西。
6. **有什麼工具可用？**

第 5 問答不出來的檢查不算檢查。粒度的差別像這樣：

- ❌「跑了測試，都過。」
- ✅「jest 42/42 通過；其中新增 6 條對應需求 R3–R5；清單與輸出在 `./tmp/validate-check-log.md`；R6 還沒有測試，矩陣上標為未證。」

## 5. 程式驗證分層表與選層決策表

依原框架的「程式碼生成」階梯改寫為 Node／ESM／Vue／mocha／jest／Playwright 環境。原則：**由低往高做；每一層都留產物；做到哪一層、哪幾層沒做，寫進回報。**

| 層 | 檢查什麼 | 怎麼做（指令） | 產物 | 這一層證明了什麼 | 這一層不能證明什麼 |
|---|---|---|---|---|---|
| L0a 可編譯可執行 | 語法正確、模組可載入、可建置 | `node --check <檔>`；`node -e "import('./<檔>').then(()=>console.log('ok'))"`；有前端就 `vite build`；有 TS 就 `tsc --noEmit` | 檢查紀錄 | 最低門檻 | 任何行為 |
| L0b Lint | 依專案既有 eslint 設定，新增錯誤數為 0 | `npx eslint <改動的檔>`；專案沒有設定就不要新增設定；不順手重排無關程式 | lint 輸出 | 語法與規範 | 行為 |
| L0c 安全與依賴 | 沒有機密或 token 進程式碼；新增的第三方依賴沒有 high／critical 漏洞；沒有 deprecated Node API 警告 | grep 金鑰樣式；`npm audit --audit-level=high`（只針對本次新增的依賴）；`node --trace-deprecation`；專案自有套件（例如 wsemi、w-*）依專案規範不提醒安裝 | audit／grep 輸出 | 沒有已知漏洞型態 | 行為 |
| L0d 實體存在（本技能新增） | 每個 import 的符號、每個用到的選項／旗標／設定鍵／CLI 參數，在**已安裝版本**中確實存在 | Grep `node_modules/<套件>/`；`<cli> --help`；官方文件；版本以 `node_modules/<套件>/package.json` 為準 | `validate-entities.md` | 沒有捏造的 API | 用法是否正確 |
| L1 單元測試 | 既有測試全綠；新增測試是需求述語的翻譯（含無效輸入與邊界）；修 bug 先有紅的重現測試再修到綠 | `npx jest` 或 `npx mocha`（專案用哪個就用哪個）；檔名前綴 `unit-` | 測試輸出＋述語對應 | 明確測到的路徑正確 | 接縫、真實資料、使用者路徑 |
| L2 整合／API | 直打真的端點、真的資料庫、真的外部 CLI，不把接縫 mock 掉 | `api-` 前綴測試、`curl`、實際 spawn | 測試輸出 | 接縫正確 | 使用者路徑 |
| L3 代表性資料 | 用真實或代表性資料集跑一遍；重構或資料處理改動要做前後輸出 diff | `./tmp/` 腳本產出改動前後的輸出，`diff` 比對 | diff 報告 | 真實分佈與邊角正確 | 效能 |
| L4 效能 | 需求載明 SLA、吞吐或資源上限時才量測 | 計時腳本、k6 等；需求沒載明就標「不適用」，不鍍金 | 量測數據 | 功能正確的程式在營運上可行 | — |
| L5 關鍵路徑 E2E＋使用者視角驗收 | `e2e-` 測試用真瀏覽器或真指令走使用者路徑；輸入空間表每一格由你實際操作一遍 | Playwright（寫法見 skill[role-coder-for-test-e2e]）；真指令實跑；截圖前驗 magic number 再讀 | e2e 輸出＋`validate-acceptance.md` | 關鍵業務路徑結果正確 | 未列入表的路徑 |
| L6 平行／影子運行 | 新舊並跑比對真實流量 | 通常超出單次交付；不做要寫明 | 分歧率 | 當前工作負載下等價 | — |

**選層決策表**（先判斷改動類型，再照表選層；把結果寫進 `validate-plan.md`）：

| 改動類型 | 必做 | 條件式必做 | 通常不做（回報要寫「不適用＋理由」） |
|---|---|---|---|
| 純函式／工具函式新增或修改 | L0a–L0d、L1、使用者視角以真指令跑一次 | 資料處理就做 L3 | L2、L4、L5 的 e2e |
| 修 bug | L0a–L0d、L1（先紅後綠的重現測試）、使用者視角重現原 bug 確認已消失 | bug 在接縫就做 L2；在 UI 就做 L5 | L4 |
| UI／互動改動 | L0a–L0d、L1（有元件測試時）、L5（e2e＋輸入空間表每格實操） | 有打後端就做 L2 | L4 |
| 涉及 HTTP／DB／檔案／外部 CLI | L0a–L0d、L1、L2 | 資料量大就做 L3 | L4 |
| 重構 | L0a–L0d、L1 全綠、L3 前後 diff 等價 | 依範圍做 L2 或 L5 | L4 |
| 需求載明效能 | 上述之外再加 L4 | — | — |

## 6. 逐步流程

### Step 0：需求述語化

1. 把需求來源（spec、issue、使用者原話）從頭到尾讀一遍，每一條可以獨立驗證的句子編一個號（R01、R02……），從原文逐行取得，不憑記憶。
2. 每條需求改寫成一到多個可驗證述語：「給定 ＿＿，可觀察到 ＿＿」。寫不出述語的需求代表還沒讀懂。
3. 問自己：使用者要的是「一句話」還是「一個類別」？使用者說「按鈕 X 會閃」，要交的是「X 所屬類別內所有同類行為都正確」，不是只修 X。把類別寫下來。
4. 有歧義時，問使用者**一個具體的點**（「R02 的『通知』是寄信還是寫 log？」），不要把整份理解丟回去請使用者 review。問不到就寫下你的假設，標明是假設。
5. 做了使用者沒要的事（效能優化、架構重整、多加的抽象）就是鍍金，屬於誤解；需求沒要就不做。

### Step 1：約束、對標、輸入空間表，選層

1. **約束清單**：列出本任務不得違反的事——不得改既有 UI 與版面、沿用既有 canonical 寫法、向後相容、不動無關的死碼、自己造成的孤兒 import 要移除。之後每個檢查點重讀一次。
2. **對標**：寫下至少兩個同類成熟產品對這件事的通用作法，以及本系統與它們的每一處差異，每一處標「刻意／補丁／缺陷」。自認很確定也要寫下來，判準是有沒有寫，不是確不確定。
3. **輸入空間表**：先列軸；每個軸的成員用 grep 從系統取得（例如可命中元素 → grep 所有 `closest('.` 選擇器；事件 → grep 所有 `@mousedown`、`addEventListener`；錯誤路徑 → grep `reject`、`throw`）；軸與軸做笛卡兒積成表；每一格填「現況（檔案:行號或實測）／應然／處置」。表上不可以有空白格。填完對照標準軸自問有沒有漏列的軸（互動類：元素 × 事件 × 滑鼠鍵 × 進行中手勢 × overlay × 能力旗標 × 終止路徑；資料流類：入口 × 前置狀態 × 並發 × 失敗點 × 事件順序 × 清理路徑）。
4. 依 §5 決策表選層。以上全部寫進 `./tmp/validate-plan.md`；需求矩陣的前三欄（需求、述語、預定檢查層）寫進 `./tmp/validate-matrix.md`。

### Step 2：實作

1. 小步前進，每一步跑 L0a。
2. 動手前先 grep 既有實作與 canonical 範例，沿用，不重複造輪子。
3. 每個 guard、排除清單、`.stop`、註解，讀到時都要能用 Step 1 的對標與輸入空間表解釋；解釋不了的標為補丁，寫進表的處置欄，不要原樣繼承。
4. 自己造成的孤兒 import、變數、函式要移除；不相關的既有死碼只提出，不刪。

### Step 3：由低往高跑階梯

1. 照 §5 的層級順序跑，每一層的指令、輸出摘要、判定寫進 `./tmp/validate-check-log.md`。
2. 任何一層紅了，就停在那一層照 §7 處置；不往上跳。
3. 新增的每一條測試，寫之前自問「這條斷言對應需求矩陣的哪一個述語？」對不上的不是測試，是現狀指紋，刪掉或回去找對應。修 bug 的重現測試要先看到它紅，再修到綠。
4. 修 bug 之後、重構之後、改測試之後，都重跑全部下層，不只重跑那一條。

### Step 4：失敗處置——照 §7 做

### Step 5：更新需求矩陣

每一層跑完，把證據（測試名、`檔案:行號`、log 路徑）填進矩陣對應的列；判定只有「已證」「未證（附待辦）」「刻意不做（附理由，須經使用者確認）」三種。一列空白就是未完成。

### Step 6：漏做掃描

逐項檢查並記錄在 `validate-plan.md` 的輸入空間表：

- 對稱性：規則套到一種元素，所有兄弟元素逐一比對；不對稱就是缺陷，不是「另一邊本來就那樣」。
- 終止路徑：mouseup、blur、destroy、旗標切換、逾時、取消。
- 清理路徑：DB、記憶體、暫存檔、子程序、事件監聽。
- 語系、平台（Windows／Linux）、角色。
- 錯誤路徑：每個成功路徑對應的失敗分支。
- 半吊子：有 hover／cursor／箭頭等承諾卻沒有對應行為、有事件監聽卻被上層丟棄、有 prop 卻無效、有 A→B 沒有 B→A——發現即列為缺陷。

### Step 7：捏造掃描（L0d）

改動檔內每個 import 的符號、每個用到的選項／旗標／設定鍵，逐一查證存在於已安裝版本，寫進 `./tmp/validate-entities.md`。查不到的就是捏造，改成真的存在的名字。

### Step 8：使用者視角驗收（L5）

1. 用真瀏覽器或真指令，對輸入空間表上每一格實際操作一遍——不是只跑自己寫的測試。
2. 每一格記錄「操作方式／觀察結果／應然／判定」到 `./tmp/validate-acceptance.md`。
3. 發現的問題全部寫進回報，包含需求範圍外的；範圍外的標明「範圍外，未修」。

### Step 9：回報——照 §8 做

## 7. 失敗處置：檢查紅了，或使用者回報 bug

照順序做，不要跳到第 6 步直接改：

1. **歸類**：這個錯是漏做、捏造，還是誤解？
2. **寫重現測試**：先讓它紅。修 bug 沒有紅過的測試，等於沒有證明 bug 存在過。
3. **找根因**：把程式碼追到 `檔案:行號`，追到底，不看表層 wiring 就推論。
4. **寫下同類判準**：什麼樣的程式碼算「同一類」？例如「所有 `:promiseUnlock="true"` 的 handler」「所有沒有處理 mouseup 的拖曳」。
5. **全範圍掃描同類**：用 grep 掃整個專案（含相關 `node_modules/<套件>/`），列成表。
6. **全部修掉**，不是只修被抓到的那一個。修法找最小改動；不翻轉並行／序列、同步／非同步這類基礎模型。
7. **重跑該層與其下各層**。
8. **更新** `validate-rootcause.md` 與需求矩陣。
9. **回報的第一段**寫歸類、根因與同類掃描結果，不是只寫「已修正」。

三件絕對不做的事：改測試或重產 baseline 去遷就現狀；把接縫 mock 掉讓整合測試變綠；只重跑紅的那一條就宣告修好。

## 8. 回報模板與完成前勾選清單

回覆末尾先貼勾選清單，全部打勾才可以寫「完成」；有任何一格沒打勾，就寫「部分完成：做了 X，未做 Y」。

```
完成前勾選
- [ ] validate-plan.md 已寫：需求述語、約束清單、對標、輸入空間表（無空白格）、選層理由
- [ ] 需求矩陣每一列都有證據與判定，沒有空白
- [ ] 實體帳冊每一項都查過已安裝版本
- [ ] 階梯由低往高跑過，每層有紀錄；失敗後下層全部重跑
- [ ] 新增測試每條斷言對應一個述語；修 bug 的重現測試紅過
- [ ] 漏做掃描六項（對稱／終止／清理／語系平台／錯誤路徑／半吊子）做過
- [ ] 使用者視角驗收：表上每一格實際操作過，發現寫進回報
- [ ] 覆蓋聲明已貼，未做的層有原因
```

覆蓋聲明的格式（每一層只能是「已做＋統計＋產物路徑」「未做＋原因」「不適用＋理由」三種之一）：

```
驗證覆蓋
- L0a 可編譯：已做，3 檔 node --check 與 import 皆通過
- L0b Lint：已做，eslint 0 error（既有 2 warning 非本次改動）
- L0c 安全依賴：已做，無新增第三方依賴；grep 無金鑰樣式
- L0d 實體存在：已做，12 項皆存在於已安裝版本（./tmp/validate-entities.md）
- L1 單元：已做，jest 42/42；新增 6 條對應 R3–R5
- L2 整合：已做，api-xxx 5/5（真 DB）
- L3 代表性資料：已做，前後 diff 等價（./tmp/validate-diff.md）
- L4 效能：不適用（需求無 SLA）
- L5 E2E／使用者視角：已做，e2e 8/8；表 24 格全部實操，發現 1 項範圍外問題（見上）
- L6 影子運行：不適用（單機工具）
需求矩陣：R01–R08 已證 8/8（./tmp/validate-matrix.md）
```

回報用語規則：

- 沒有矩陣與覆蓋聲明，不可以寫「完成」「全盤」「全部」。
- 沒有實測過的行為一律用「推測」「看起來」「可能」並加註「需實測確認」。
- 失敗後的回報第一段寫根因與同類掃描結果。

## 9. 反模式與正確作法對照

| 錯的做法 | 為什麼錯 | 正確作法 |
|---|---|---|
| 改測試或重產 baseline 去遷就現狀 | 把偏離 spec 凍結成真理 | 修系統或修 spec，不改測試將就 |
| `buf.equals(baseline)` 當測試 | 現狀指紋，不是 spec 翻譯 | 語意斷言為主；像素比對用容差當補強層 |
| 把接縫 mock 掉後說整合已驗 | 沒有測到接縫 | L2 直打真端點、真 DB、真 CLI |
| 紅了只重跑那一條測試 | 修正可能弄壞別的 | 重跑該層與其下各層 |
| 「tests pass」＝完成 | 鐵則二 | 三件完成判準（§0） |
| 沒查 `--help` 或 `node_modules` 就用旗標、函式名 | 捏造 | Step 7 實體帳冊 |
| 只修投訴的那一點 | 誤解（類別縮成一句） | Step 0 第 3 點、§7 同類掃描 |
| 兄弟元素不比對；終止與清理路徑不做 | 漏做 | Step 6 漏做掃描 |
| 需求含糊自選解釋不說 | 誤解 | 問具體那一點，或寫下假設 |
| 做需求沒要的效能、架構、抽象 | 鍍金；為消除假想風險引入確定退化 | 沒有「已被觀察＋後果具體」的問題不主動做，寫進已知不修 |
| 「只改一行」不重跑階梯 | 鐵則三 | 每次改動全部重跑 |
| 讀程式碼推論出來的行為寫成「實測過」 | 捏造 | runtime 行為只能以實跑為證 |
