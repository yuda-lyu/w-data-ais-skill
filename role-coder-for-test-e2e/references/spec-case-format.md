# spec「重要流程」之 E2E-NNN case 撰寫格式

適用於 `spec/流程_*.md` 的「重要流程」章節；每個 `E2E-NNN` 以三層 bullet 撰寫。與流程文件撰寫技能（scope 紀律、呼叫鏈 `[file:line]` 格式）並存——那是上位規則，本篇只規範 E2E-NNN bullet 內部怎麼寫。

**一份 spec 有兩種讀者**：`description` 給**系統使用者**（將來直接移作操作手冊），`flow` 與〈畫面元素對照〉給**實作者**。兩者受眾不同、寫法不同，不可混寫。2026-09 高放主系統之 140 條 description 全部寫成測試理由書、被業主整批退回，是本篇第 2 節的直接來源。

## 1. 三點結構（順序固定，缺一不可）

- **title**：一句話（≤ 25 字）說「在使用者觀察視角這個 case 做什麼」。動詞落在使用者視角（成功登入、顯示錯誤訊息、轉址至某頁），不寫後端機制。具名範例以「（以某具名項目為例）」附於 title 尾。
- **description**：操作手冊敘述文字，寫法見第 2 節。
- **flow**：契約等級的測試藍圖，固定 bullet：

| # | bullet | 寫什麼 |
|---|---|---|
| 1 | 測試資料 | seed 的關鍵欄位語意值、具名項目（資料編號、節點文字）、登入身分與所需權限；需要之 fixture 若尚未建立須明標「尚未建立」 |
| 2 | 操作 | 起點頁 → user-facing 動作用 `→` 串接，按鈕名照畫面原文；**每案自述完整前置**，不寫「承 E2E-001 之狀態」（案例互相依賴會與 per-case 隔離衝突） |
| 3 | 驗證 | 「語意」（DOM 文字 / URL / 元素存在性）+「視覺」（baseline 檔名 `test/pics/<flow>/<flow>[-<lang>]-E2E-NNN[-<階段序>]-<kebab>.png`）；比對採感知容差為全專案統一機制，不逐 case 複述；共用他 case 的 baseline 寫明「共用 `…png`，不另設標準圖」。**視覺項以「操作序列」列出**：每個操作兩張——點擊前框住要點的位置（`<序>-click-xxx` / `type-xxx` / `check-xxx`，括號寫框住什麼）→ 點擊後之結果（括號寫框住哪個**元素**：具體到「01/02/03 三列」「整顆標籤含圖示」「整個抽屜面板含標頭」「全螢幕的最大化彈窗」，不寫「框住區域」「框住右欄」；一張圖只一個框；目標被彈窗蓋住時寫「框住彈窗，原標籤位於彈窗之後不框」）；走到產品缺陷的步驟寫「此圖不產製，偵測到徵狀即標 pending，缺陷修復後補產」；下載類至少有點擊前那張並寫明無畫面終態；同 flow 內首個 case 寫一次通則（每步兩張、一圖一框、框實際內容不框空白）與檔名前綴，其餘 case 只列序列 |
| 4 | 雙語 | 有 i18n 者「各語系一輪」；單一語系專案省略此 bullet 並於共用約定載明偏離 |
| 5 | 清理 | 依副作用類型寫具體處置（見第 5 節），不得只寫「由下一案例之資料庫重置回復」 |
| 6 | 備註（選用） | 實作者才需要的技術資訊：不可達路徑之證據、`檔案:行號`、階段截圖規劃、與他案之對稱關係、fixture 限制 |

## 2. description：操作手冊敘述，受眾是使用者

### 2.1 定位

description 將來**逐字移作操作手冊**。寫的時候把自己當手冊的引言者：告訴使用者這功能在哪、怎麼做、會看到什麼、什麼時候用得上。不是在對測試撰寫者交代這個 case 要驗什麼。

### 2.2 寫成什麼

- 骨架「在哪裡 → 做什麼 → 看到什麼 → 什麼時候用得上」。
- 主語是使用者或系統，直述操作與結果；不以「驗證」「本案例」起頭。
- 畫面上的按鈕名、欄位名、訊息文字**一律照抄**；含變數者以 `[資料編號]`、`{處數}` 佔位，不可簡化成「顯示成功訊息」。
- 用途以「便於…」「適合…」「可用於…」口吻。
- 補充以逗號接「此時」「其中」「亦即」展開成句，不用括號夾註。
- 具名測試對象可保留，以「以…為例」語氣呈現，避免讀成永久產品行為。

### 2.3 不得出現（以句型與受眾判準，不採詞彙黑名單）

| 類別 | 例 |
|---|---|
| 以測試為主語之句型 | 「本案例為…之驗證」「本案例含兩階段截圖」「兩者成對構成…之契約」「使讀者能看到完整之逐層點擊軌跡」 |
| 對測試撰寫者之指示 | 「撰寫 e2e 時須等待…再行截圖」「此差異須於 spec 明載」 |
| 程式碼位置與識別字 | `src/…vue:406`、組件名、prop 名、變數名、`panelWidth<500` |
| 案例編號交叉引用 | 「與 E2E-003 為同一按鈕之兩條分歧路徑」「本案例為 E2E-006 之反向契約」 |
| 截圖階段編號 | `stage1`、`stage2` |
| 可改寫成正文之括號夾註 | 「顯示座標軸與網格（尚未載入任何模型）」→「顯示座標軸與網格，此時尚未載入任何模型」 |
| Markdown 強調 | 「在**不勾選**自動升版之情形下」→「在未勾選自動升版的情況下」 |
| 需求對應語 | 「本案例對應使用者需自大量源項資料中查找特定機組之需求」→ 改寫成用途句「可用於自大量源項資料中查找特定機組」 |

**不禁止**：產品名稱與縮寫（GIS(2D)、FEPs、SNF）、畫面原文中的括號（「下載數據成為 Excel(xlsx) 檔案」）、單位與格式範例（`R00.01`）、使用者要照字面輸入的網址參數名（`view_mod`），以及專案領域詞——「階段」（計畫階段）、「驗證」（審查與查證）在敘述資料內容時是正常用語，只有作為測試語彙時才禁。詞彙黑名單會誤殺領域詞，故判準一律看句型與受眾。

### 2.4 必須保留的資訊（改寫時最常被一起刪掉的）

讀完 description 後，使用者要能回答六個問題；答不出任一即不合格：

1. **入口與權限**：從哪裡進入（「右側內容區上方操作列的…」而非「操作列的…」；圖示鈕寫其提示文字，如「左側目錄區上方的加號按鈕，提示文字為「新增知識管理項目」」）；需要什麼權限才看得到（「僅具編輯權限的使用者看得到」）。權限是手冊最常被問的問題，一條都不能漏。
2. **必要前置**：需先完成什麼（先解除圖台鎖定、先選擇資料夾、先切到某分頁）。
3. **不可逆效果**：刪除可否復原、是否連帶影響其他資料。
4. **是否已寫入**：完成後資料是否已進資料庫，或仍需另按儲存。
5. **成功識別**：成功後畫面顯示的訊息原文，或可據以確認的欄位。
6. **失敗如何處理**：被攔截時看到什麼、關閉提示後停在哪、如何修正後重試。

另兩項手冊必要而 spec 撰寫者常省略的：**送出方式**（「按 Enter 或點右側「添加關鍵字」圖示」，不寫「輸入並送出」）與**可照抄的範例**（網址參數類一律附一組完整範例網址與各參數值域）。

### 2.5 驗收方式

不以句數為準（二至四句只是建議），以語意檢核：逐條對 2.4 六問。機械掃描（`本案例|驗證使用者|截圖|stage[0-9]|E2E-\d|src/|\*\*|（[^）]{2,}）`）只能抓表面違規，抓不到「刪過頭」；兩者都要做。

### 2.6 移除的技術資訊放哪裡

description 拿掉的 `檔案:行號`、階段截圖規劃、案例間對稱關係、不可達之證據，一律放 flow 的〈驗證〉或〈備註〉，以及各檔〈畫面元素對照〉表；該二處讀者為實作者，維持原有精確度，不做刪減。

### 2.7 用詞統一

同一動作在全部文件用同一詞：恢復先前顯示狀態一律「恢復」（「還原」只用於按鈕原文「還原變更」）；選取清單／樹狀項目用「點選」、按鈕用「點擊」；「從主選單點選「X」後」而非「自主選單點入」（後者易讀成「自主的選單」）。

## 3. 契約等級，不是 code-mirror（flow 部分）

判別句：「production code 改 100 行、helper 全部重新命名，這條 flow 還能讀懂、還是同一個契約嗎？」是 → 留；否 → 丟。

| 保留（契約） | 丟掉（實作細節） |
|---|---|
| 測試資料的欄位語意值 | helper 函式名（`insertTestUsers`、`startServersOnce`） |
| 使用者操作層級（點按鈕、輸入欄位） | Playwright API（`page.locator`、`keyboard.insertText`） |
| 應觀察到的 UI 文字、URL、DOM 終態 | 固定 wait 數字 → 改「等待 redirect 完成後」 |
| baseline 檔名路徑 | 比對 API（`assertBaselineMatch(...)`） |
| 語系清單 | 內部 mode 旗標 / 常數 |
| 清理範圍與副作用類型 | DB / ORM 字面、後端呼叫鏈、selector 字面 |

`檔案:行號` 在 flow 的〈驗證〉〈備註〉與〈畫面元素對照〉是**允許且鼓勵**的（實作者要找得到），只有 description 不可出現。

## 4. 事實來源與可達性

- **spec 一律以現行程式碼與實機行為為唯一事實來源**。過往版本之說明文件、需求書、架構文件**不得**作為依據，亦不得拿來與現況比對後寫成「已知落差」——舊文件落後於實作是常態，不是問題。〈已知落差〉只收錄由程式碼或實機行為本身證成的不一致（同型元件互動不對稱、承諾未兌現、同一語意兩處行為不同）。
- **具名測試對象取自現行資料庫確實存在之項目**，且資料庫重建後須逐一複驗（筆數、版本數、欄位值、清單文字）；匯入當下寫入的日期欄位（上傳時間、變更時間）每次重建都會漂移，須遮罩而非斷言。
- **具名測試對象依變體列舉，並選結果最豐富者**：同一功能有幾種資料型別（由 schema／解析器型別得知）、幾種內容型別（由附件分組欄位得知）、幾種入口（滑鼠／鍵盤），spec 的〈測試資料〉就要各列一筆具名對象，並寫明選它的理由（多分頁、多命中、多版次）；同名前綴會混淆的對象要寫出唯一化的比對字串。只列第一筆或最簡單那筆，實作者就只會測那筆。
- **寫案例前先確認路徑可達**：按鈕的 `v-if` 條件是第一個要看的。三個踩過的坑——①「未變更即儲存」的警告只在編輯模式且無變更時觸發，而該狀態下送出鈕根本不渲染；②「未選檔即上傳」的提示在按鈕外層 `v-if="files.length>0"` 之內，未選檔時按不到；③「無報告即下載」同理。這類提示是防禦性程式碼，**不設 e2e 案例**，於〈訊息對照〉標「UI 不可達」並附條件。
- **權限負向案例必須先滿足狀態條件**：兩顆按鈕在「尚無檔案」「尚無報告」時對有無權限者都不渲染，在初始空畫面測權限會假通過。先把狀態推到有權限者確實看得到按鈕，再換無權限帳號比對。
- **案例廢止保留編號，不順移**：`E2E-NNN` 已被 baseline 檔名、對照表、外部複審引用；廢止的案例改成單行「（已廢止，編號保留不再使用）」附廢止理由，後續編號不動。
- **標籤／chip 類元素先查有無 `@click` 與 `cursor:pointer`**：同型元素在不同系統可點與不可點不一致（KMS/RMS 可點、FEPs 不可點）是常見情形，不可以「各系統皆可點」概括，不可達者不設案例並記入已知落差。

## 4.1 跨流程共用文件之檔名與內容

- **檔名固定為 `spec/設計要點與取捨.md`**（w-web-sso 首創，perm / api / 高放主系統沿用），不自創「共用約定」「共用規則」等別名——同組織的專案要能用同一路徑互相引用。
- 內容兩類，同一檔：①**跨流程設計決策**以 ADR 段落記錄（`ADR-NNN`：Status / Context / Decision / Consequences / Affected；修改時新增並把舊條標 Superseded，不刪舊條）；②**各流程 spec 共通之約定**（文件範圍與命名、語系、標準圖命名與 flow 代號登記、資料庫重置與副作用清理對照、軟／硬刪除語意、共用元件之驗證歸屬、截圖穩定性處置、訊息取用方式、事實來源、description 撰寫風格、待業主裁示彙整、變更紀錄）。
- 各流程 spec 與本檔衝突時，以流程 spec 明文為準並於該處說明理由（視為刻意之個別偏離）。
- 專案 `CLAUDE_settings.md` 之 e2e 映射與本檔之 flow 代號表須一致，新增系統時兩處同步。

## 5. 副作用與清理對照

資料庫重置只回復 DB。案例會產生下列副作用者，〈清理〉須逐項寫處置，並於共用約定建對照表：

| 副作用 | 清理 | 可否由 DB 重置回復 |
|---|---|---|
| 資料庫資料列 | 快照複製或完整重建 | 可 |
| 上傳落地之實體檔案 | 案例自行刪除，或完整重建含目錄 | 否（快照不涵蓋） |
| 伺服器暫存與批次資料夾 | 呼叫清空作業並回驗目錄已空 | 否 |
| 使用者下載之檔案 | 案例結束後刪除 | 不適用 |
| 原始碼目錄之產生檔（如 schema 定義檔） | **不可於主工作樹執行**；成功路徑於可拋棄副本或 `api-` 層驗證 | 否 |

## 6. 跨 case 連結（只寫在 flow 與備註）

- **baseline 共用**：驗證 bullet 檔名後加註「與 E2E-XXX 共用」；description **不**提。
- **對稱關係**（新增↔刪除、確定↔取消、節點↔連線）：備註寫「與 E2E-XXX 為對稱路徑」，用於盤查漏格；description 不提。
- 只引本文件內的 case，不引外部 `spec/流程_*.md`。

## 7. 寫完前自問

1. title 是使用者觀察視角？
2. description 逐條過 2.4 六問，且機械掃描零命中？
3. description 的按鈕名、訊息文字與程式碼逐字相符（含全形／半形、空格、大小寫）？
4. flow 每案自述完整前置、清理寫到副作用類型、備註承接了 description 拿掉的技術資訊？
5. 每個案例的操作路徑已對照 `v-if` 確認可達？權限負向案例已先滿足狀態條件？
5b. 〈測試資料〉已依資料型別、內容型別、入口列出各一筆具名對象，且為結果最豐富者？
6. 共用 baseline、對稱關係只寫在 flow／備註？
7. 沒有引用任何舊版說明文件？已知落差每條都有 `檔案:行號` 或實測證據？

新寫 case 前先讀該專案既有 `spec/流程_*.md` 對齊風格，不從零自創。
