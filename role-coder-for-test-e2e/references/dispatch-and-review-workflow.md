# 多系統批量產製：主代理派工、探測、排程與審圖流程

本篇是 SKILL.md §1.5 的深入層。適用情境：同一專案要為多個子系統（或同一系統多批案例）產出 e2e 與標準圖，工作量超過一個 context 能穩定承載，或需要把「品質把關」與「大量實作」分給不同角色。核心分工：**主代理只做三件判斷密集的事——決定表、審圖、消化退件；子代理做實作與產製**。以下流程依序執行，每步有產物；跳步的後果寫在各步末尾。

## 1. 分工與模型

| 角色 | 做什麼 | 不做什麼 |
|---|---|---|
| 主代理（最強模型） | 勘查與探測（§2）、寫計畫檔（§3）、排程（§4）、逐張審圖與退件（§5）、對使用者回報（§6） | 不親自寫大量案例（會把 context 耗在實作細節，審圖時已無餘裕） |
| 子代理（每系統一個，全新 context；實作用次一級模型即可） | 依計畫檔實作 helper／案例／spec／映射表、產製、自審、寫目視紀錄、回報 | 不改決定表；不自行放寬 strict／容差；不跑 mocha 比對新標準圖；不動他系統之檔案與標準圖 |

為什麼每系統一個全新 context：長 session 壓縮後會重犯已修過的錯；新 context 讀「計畫檔＋前一系統的成品」比讀一大段對話便宜且準確。**前一系統的成品即下一系統的範本**（測試檔結構、helper 分層、spec 寫法），派工 prompt 直接指名。

## 2. 派工前的探測（主代理做，不可省）

計畫檔裡的每一個「事實」都要來自實機，不是來自 spec 或讀碼推論。派工前先寫探測腳本（Playwright 直跑，走與正式案例相同的 launch wrapper、登入、進站），取得：

- **可行性**：新技術在測試環境能否出圖（例：WebGL 在 headless 下是否有軟體渲染、外部瓦片是否可達、圖片瀏覽器是否能開）。可行性決定遮罩／覆蓋策略，先於一切決定表。
- **資料事實**：具名測試對象的編號、名稱、版次、筆數、分頁清單、區塊清單；同名前綴的干擾項（例：關鍵字「X」同時命中「X 電廠」與「X 應變區」時，計畫檔要寫出唯一化的比對字串）。
- **DOM 結構與可點層**：元件的真實 hit target（自訂圓鈕的 `span`/`svg` 常不是可點層，`locator.click` 會逾時，須改矩形中心真滑鼠點擊）、內部捲動容器是哪一層（排除同樣 `overflow:auto` 的分頁列）、工具列按鈕如何識別（tooltip 只在 hover 才出現時以順序＋SVG path 起頭核對）。
- **互動語意**：點清單項是平移＋彈窗還是直接開抽屜；平移後主體落在畫布哪裡（決定後續放大要以游標為錨）；全畫面覆蓋層如何關閉（點背景／Esc）。

產物：探測腳本 `tmp/zz_*.mjs`、log、截圖；計畫檔逐條引用。探測腳本的收尾紀律見 SKILL.md §11.4——**失敗路徑也必須關瀏覽器並強制退出**，否則串接在它後面的等待會永遠卡住（殷鑑：一支探測拋錯後 node 掛著 40 分鐘，後兩支探測與一位子代理全在等它）。

## 3. 計畫檔（子代理的規格，不是建議）

一份計畫檔 = 一個或一組同骨架系統。固定段落：

1. **骨架與差異**：同骨架系統以「系統設定物件」參數化（主選單文字、標題、容器 class、訊息模板、欄位集），逐項列表；差異只在文案／class／欄位者共用 helper，案例仍逐檔明寫（讓每檔可獨立閱讀與審查，不做案例工廠）。
2. **實測事實**（§2 之產物，附 log／截圖路徑）。
3. **決定表**：每案例每一步兩張圖（點擊前框要點、點擊後框反應）、檔名、框住什麼、語意斷言對應 spec 哪句（格式見 baseline-as-manual §2）。表填滿才派工；表上空格＝派工後的返工。
4. **程式結構**：helper 分層（通用 DOM 層／同骨架共用層／單系統專屬層）、新增與不可改動之清單、產製與比對之分岔點（如畫布覆蓋只在比對端）。
5. **工作規則**（§4 排程規則、暫存路徑、act 層級、不跑 mocha、壞畫面不凍結、產完必掃描＋逐張目視＋寫紀錄）。
6. **交付清單**：改動檔案、案例對照表、目視紀錄與統計、spec 修改摘要、發現之缺陷、回歸結果、未做之處、每個 helper 的定位判準一句話、實測值。

派工 prompt 只需指向計畫檔＋技能＋範本檔＋探測產物，並重述硬規則（違反即退件）。

## 4. 排程：共用後端與資料庫時只能一條產製鏈

- 產製鏈（重產、mocha、探測）共用同一組後端與資料庫，**同一時間只能有一條**；每條啟動前確認上一條已結束（任務完成通知、`netstat` 埠已釋放）。
- 子代理可並行**寫程式**，但啟動服務／瀏覽器前必須通過閘門。可靠閘門是**主代理建立的旗標檔**（`until [ -f tmp/<x>.flag ]; do sleep 10; done`），在前一條鏈確認結束後才建立；不要用「等某 log 出現 EXIT」（log 名重用會匹配到上一輪、腳本卡死時永遠不出現）。
- 每條鏈用**沒用過的 log 名**；以任務完成通知或本輪 log 為準；異常時以圖檔 mtime 對照本輪起訖判斷哪些圖真的產了。
- 長鏈沉默超過預期時間（探測 3 分鐘、單系統產製依案例數估）即查程序清單（以命令列比對，只殺自己啟動的），不憑「應該還在跑」空等；使用者問「怎麼這麼久」時，答案必須是具體的卡點與處置，不是「還在跑」。
- 第二批追加案例到既有測試檔時：只以 `--names` 產新案例；產前記下既有圖之 mtime，產後回驗一張未變；既有標準圖不得被重產（重產等於把已審過的圖換掉）。

## 5. 審圖與退件（主代理逐張看，掃描只是輔助）

1. **紅線掃描**每張恰一框；場景／圖表本身的紅色（標籤、地層、警示）會造成假陽性，掃描異常者以人眼判定。
2. **逐張 Read 看圖**，對照決定表核對：框對元素、整顆、無空白、無切邊、無壞畫面、頁首未被切、前後張版面一致。行動類的「點擊前」圖要看框住的位置下方有沒有會誤導讀者的東西（例：點背景關閉覆蓋層時，框在被壓暗的主選單項上，讀者會以為要點主選單——改到明確無物的區域）。
3. **子代理的主張要對物核實**：子代理說「既有標準圖也有同樣問題」「此為元件既有行為」時，主代理自己開既有圖或探測再下結論（殷鑑：子代理稱既有查詢標籤圖只框到文字，實際查看兩張皆已框整顆；若照單全收會無故重產已審過的圖）。
4. **退一張＝退一類**：退件訊息寫類別與判準，要求同類全掃後重產，並確認其他圖 mtime 未變。
5. **接受刻意偏離的條件**：子代理依技能既有規則做出的偏離（例：新分頁自動開了彈窗就框彈窗、`fullPage` 觸發重排改用視窗截圖）可接受，但須寫進 spec 該張的括號說明與映射表〈偏離與依據〉。
6. 程式面抽查：grep act 層級（`.fill(`／`dispatchEvent`／`vm.`／`$store`／`evaluate` 設值）、`node --check`、匯入解析、埠已釋放、`./tmp` 清理、`testPending` 無本輪新增。

## 6. 回報與交審

- 依系統列：案例數、圖數、退回類別與修法、發現之產品觀察（分「非測試問題，已寫入 spec 已知落差」與「疑似缺陷，需使用者裁示」）。
- **未經使用者審圖不跑 mocha**。回報明寫「待審圖認可後跑 mocha 全跑與 `--grep` 單跑一致性」。
- 使用者追加範圍（「X 功能沒做到」）時，先回到 §2 探測該功能的事實，再補計畫檔決定表，再派工；不憑對話印象直接改案例。

## 7. 常見失敗與對策（本流程專屬）

| 失敗 | 對策 |
|---|---|
| 計畫檔的事實取自 spec／讀碼，實機不符（版次、筆數、冒號、圖示名） | §2 探測先行；spec 錯誤由子代理改 spec 並列〈已知落差〉 |
| 兩條產製鏈並行互殺後端 | §4 單鏈＋旗標檔閘門 |
| 探測腳本失敗未關瀏覽器，串接等待卡死 | §2／SKILL §11.4 收尾紀律；等待迴圈以殼層寫入之行首標記為準 |
| 覆蓋／貼回之目標選擇器永不命中，功能形同未實作 | 每個目標選擇器都要有命中數自測（SKILL §8.2） |
| 首圖之即時數值（資源監控）各流程各自處理或漏處理 | 動態區域之處理集中於共用層一處，所有流程呼叫同一函式 |
| 子代理以探測用的捷徑（程式捲動、`locator.click` 自動捲入）製造假現象（主選單被捲動）並當成產品問題 | 探測與案例都走使用者動作；現象要先在正式進站路徑重現 |
| 審圖只看掃描結果 | §5 逐張看；掃描回答「有沒有框」，回答不了「框對不對」 |
